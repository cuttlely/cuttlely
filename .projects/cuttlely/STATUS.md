# Status

Last refreshed 2026-10-13. Check `git log origin/main` for anything newer.

## What works on `main`

Cuttlely 1.0.3. The product version is the root `package.json`, `packages/server/package.json`, `packages/cli/package.json` and `packages/chat-widget/package.json`. The About dialog reads the server one. The root package name is `cuttlely-workspace` so the published launcher can be named `cuttlely`. The server package is `@cuttlely/server`, the UI package is `@cuttlely/ui`, and the API docs package is `@cuttlely/api-docs`.

-   **Agent teams (harnesses).** A harness is a named team: Harness Prime routes each question, specialists do the work in parallel, and Prime writes one answer. Specialists use canvas tools, retrievers, vector stores and MCP servers in process, and the agent runtime for Shell, Browser, Code execution, Files and MCP work. Any chat-model node can drive Prime or a specialist, with an optional fallback model. Turns stream over the prediction API, have a wall-clock budget, cap their context tokens, and report tokens and timings. Each harness has a run history page with a playground.
-   **Analyst.** A specialist with its own isolated database (`CUTTLELY_ANALYST=auto`, or a separate Postgres URL) that creates tables, answers from real rows and pages long results. The page size is 100 rows and the statement timeout is 15 seconds unless **Admin** > **Server settings** > **Analyst** changes them (`CUTTLELY_ANALYST_ROW_CAP`, 1 to 1000; `CUTTLELY_ANALYST_STATEMENT_TIMEOUT_MS`, 1 to 120 seconds). The server clamps both. A PostgreSQL MCP node can ask for a lower cap or a shorter timeout, never a higher one. A legacy `analyst.db` is claimed by the first workspace through an exclusive link. A query step on the run card shows how many rows that query returned and a short preview of them. The preview is stored with the run trace and only includes rows that query already returned, never more than the configured row cap, and it is also capped in bytes. **Admin** > **Server settings** > **Analyst** can turn previews off (`CUTTLELY_ANALYST_TRACE_PREVIEW`). A run saved before previews still opens.
-   **Knowledge pipelines (ETL).** A pipeline canvas with streaming sources, incremental upsert into any vector store, every text splitter and embeddings node, schedules, run history, and the ETL Retriever for chatflows and harnesses.
-   **Chatflows and agentflows.** The visual canvas and node catalog, with Build with AI on every canvas. Older V1 agentflows still run but are not offered for new work. Optional node packs load from `CUTTLELY_NODE_PACKS` (a directory or a package whose `package.json` declares `cuttlely.nodePack`). The packs that ship with the install always load. Today that is `@cuttlely/node-pack-vector-stores` (vector store nodes, the credentials only they use, and the dependencies only they import), `@cuttlely/node-pack-tools-mcp` (tool nodes that call an outside service, the prebuilt MCP server nodes for those services, and the credentials and dependencies only those nodes use), `@cuttlely/node-pack-caches-memory` (cache nodes and memory backends that use an outside service, the credentials only they use, and the dependencies only they import), and `@cuttlely/node-pack-legacy-chains` (completion model nodes, the chain nodes that carry the DEPRECATING badge, the credential only those nodes use, and the dependencies only they import). Custom Tool, Custom MCP, chatflow and agentflow tools, Retriever Tool, Calculator, Request tools, the ETL Retriever, and the PostgreSQL MCP node the analyst uses stay in `packages/components`. Buffer Memory, Buffer Window Memory, Conversation Summary Memory, Conversation Summary Buffer Memory and the agent memory nodes stay there too. `CUTTLELY_NODE_PACKS` adds packs on top. A blank value adds nothing. `INCLUDE_NODE_PACKS=0` skips the shipped packs. A saved flow that uses a node that is not installed opens with a placeholder card that names the pack and keeps the lines into that card, export leaves that node's data as saved, and a prediction returns 422 with a plain message. When the saved node has no `nodePack`, the card and the 422 use `packages/server/src/utils/node-pack-index.json` (node name and label to package name), generated by `scripts/build-node-pack-index.mjs` from `packages/node-pack-*/nodes`. The server build and the image build check that committed file and copy it into `dist` before a slim image leaves the packs out. They do not rewrite it. `GET /api/v1/nodes/pack-index` returns that list. A save or an import writes `nodePack` from the index when the field is absent (D54). [Optional node packs](../../docs/how-to/node-packs.md).
-   **Drafts and version history.** Chatflow, agentflow, harness, and pipeline canvases save to a draft; Publish makes that draft Live, and Roll back sets Live to an earlier version. The harness canvas chat and Try it run the draft when one exists, including its specialists, tools, and models. A draft try uses its own gateway token and a marked try profile, so a published run stays on the saved harness while the try is in flight. SQL tools refused on a try stay on that try's profile, and the analyst page stays on the saved harness. A harness cannot be saved or imported under a name that matches a try profile. A specialist profile id that would pass 64 characters keeps a short hash of the full name; an id that already fits is left as it is. When the harness name itself leaves no room, that profile is `tryx` plus 16 hex and is removed by its parent marker when the specialist goes away. A canvas try closes the runtime profile for that try and each specialist, then removes those directories and checks they are gone, retrying a few times. A directory that is still there is logged once. Startup removes a try left behind by a crash, token included, only when that directory carries the try marker and it is not a saved harness, and it removes the specialist directory named with that try and a `--` suffix. A directory without the try marker stays. An in-flight try keeps a lock file in its directory, tied to that process, so another process does not remove it while the same process is still running. A specialist directory left after its try directory is gone is removed on the next start, and its token is not loaded. `POST /api/v1/harnesses/:name/runs` keeps serving the published roster until Publish. A pipeline canvas saves to a draft. Scheduled runs, a run you start, and a full rebuild keep using the published pipeline until Publish. Preview runs the draft and does not write to the store. The Publish dialog lists what changed and does not run the question check. Restore, a check that replays a chosen number of recent real questions before Publish (4, 10, 25, 50, or 100; 4 by default; chatflows, agentflows, and harnesses) or the rows of a saved dataset scored with selected evaluators, and the same check for an agentflow that starts from a form, a webhook or a schedule, replaying that many distinct recorded inputs from recent executions and showing where each one came from and when it was recorded (the box is titled Check recent runs from the canvas before the check request returns; with none, the dialog says how to create a run; when fewer runs exist than the choice, the picker is labeled Requested runs; a dataset check on that start is refused). Turning the passing test set on is refused for a form, webhook, or schedule start, and the configuration hides it while it is off. If the start changes after the setting is on, Publish stays refused until it is turned off. A harness check replays that many distinct full prompts from saved chats on the Live roster and the draft roster, each through its own try profile, and writes no run history, session, or analyst capture. History can also keep an optional copy in GitHub, with promotion along an ordered list of environments, and Dev to Prod promotion. Promote runs that check on the receiving server against that server's own questions or executions. On a longer list, the review page for one flow shows the version each environment has of it. The check column stays From Dev on the saved pair and names the previous environment otherwise. A saved Dev or Prod label is still dev then prod. Promotion moves only to the next environment, and each hop keeps the behavior check and the credential-name check (D57). Each server stores the list. A publisher records a fingerprint of it with the copy, and that copy is not finished until the fingerprint is recorded. A reader offers new versions only when the fingerprint matches. Once any fingerprint is recorded, a different list or a version with no fingerprint is not offered. The only read that still accepts versions with no fingerprint is the saved Dev and Prod pair, when the repository has no fingerprint record at all. A named list installs a tip only when the note on it matches. A named Prod whose record is missing keeps the versions already offered and offers nothing new. A list change that keeps what this server reads and copies rewrites that fingerprint on the versions already copied. A named list with no environment chosen does not count versions as waiting, and connect is refused until one is chosen. A later environment cannot connect unless the previous branch's tip carries this server's recorded list, so a README-only branch, a note on another commit, or a different list is refused and nothing is saved or copied. The check and that first copy use the same list. An environment-only save does not repair a list that cannot be read. A connection file that cannot be read is reported separately, so the card and the promote page keep the saved list. Saving the saved pair does not replace a named list that still parses. A chatflow or agentflow can require that dataset check to pass before Publish (D64). The setting is off until it is turned on. The dataset and every evaluator must already exist in the flow's workspace, and the dataset must have a question the check can ask. A missing id, or one from another workspace, is 404 and nothing is stored. An agentflow that starts with a form, a webhook, or a schedule is refused the same way a dataset check on that start is. The configuration hides the setting while it is off. If the start changes after the setting is on, the setting stays visible so it can be turned off, and Publish stays blocked until then. Turning it off does not need permission to view datasets or evaluators. Publish then returns 409 unless the latest stored result passed for the current draft, the current dataset, evaluators, and pass mark (0 to 100, 100 when omitted), and the same asked rows and evaluator configs. Errored scores count as not passed. The stored result is the draft hash, the settings, a hash of the rows that check asked and of each evaluator's type and config, the pass rate, the counts, the verdict, and the time. It does not include answers. If storing that result fails, the check is failed and the stored result is cleared, so an older pass cannot publish. If that clear also fails, this process refuses the older pass. A restart or another process can publish it again if it still matches. Turning one of Publish instantly and the passing test set on is stored only while the other is still off. Publish reloads those rows and evaluators in the flow's workspace. A different hash, a missing dataset or evaluator, or a change to the flow's answer post-processing, makes that pass out of date. The hash is of the rows and evaluators that check scored, from that one read. Rows that share a sequence are ordered by row id. Save, discard, and the settings update return that same refusal. A harness uses the same Publish route and is not covered: the setting is refused for a harness, and a harness check does not store a pass. A direct chatflow update, Restore straight to Live, Roll back, and Promote from Dev still change Live. With the setting off, Publish is unchanged. `cuttlely check` runs that check from a pipeline and exits 1 when `--fail-on-changed` sees a Changed answer. With `--dataset` or `--gate` it runs the dataset check and exits 0 or 1 on the server verdict (D71). `--gate` exits 2 before a check starts when the read withholds the dataset id or the evaluator ids, and it reads the flow again after a pass so a changed test set does not exit 0. [Fail a build when answers change](../../docs/how-to/ci-gate.md).
-   **Share and embed.** The `@cuttlely/chat` widget, served by the server at `/embed/chat.js`, for share links and website embeds, including charts on cross-site embeds that the chatflow allows.
-   **API.** Chatflows, agentflows and harnesses through `POST /api/v1/prediction/:id`, with document uploads, streaming, caller-owned sessions and hashed API keys. `docs/api.md` and `examples/web-app/` show a real app.
-   **Token totals over time.** A finished chatflow, agentflow, Multi Agents canvas, Sequential Agents canvas, or harness run adds its input and output tokens to `token_usage_day`, keyed by workspace, flow, model, and UTC day. A chatflow whose only node is a harness stores the team's tokens on the chatflow. A Tool Agent that calls the harness tool records that same payload on the chatflow, because the tool text has no counts. The harness model calls are not also added by the chatflow counter. A harness run started from the harness API, a harness canvas draft try, and a harness publish-check replay stores them under the harness name. Each of those is the same write as the public run, once. An ordinary chatflow, and a Multi Agents or Sequential Agents canvas, record the token counts the model calls already reported. An Agent step that calls tools stores the sum of each model call, including calls from before a tool approval, a structured-output conversion, and a memory summary. The step cost and the execution chip's token total use that same sum. A loop that finishes a pass and later stops for approval keeps the finished pass. A Sequential Agents interrupt saves the waiting action on the chat message before that action is streamed, and writes the daily total when the run finishes. A resume reads that saved action and ignores usage sent on the request. An action with no saved id fails the resume and writes no partial total. An agentflow Agent that calls a harness records that harness payload on the agentflow together with the Agent's own calls. `GET /api/v1/stats/usage` returns the daily totals and the totals per flow for 7, 30, or 90 days (`days`, or `range` as `7d`, `30d`, or `90d`), or a custom range, filtered by flow and model. `range` cannot be combined with `days` or a start or end date. The caller needs `chatflows:view` or `agentflows:view`, and so does `GET /api/v1/stats/:id`. A failed write does not change the run. A publish check counts toward the total. `GET /api/v1/stats/usage` also returns an estimated cost per day, per flow, and per model, computed when the route is read from the current model prices (D62). A model with no price is `no price`, not zero. An organization owner can override a model's input and output price, in US dollars per million tokens, with `PUT /api/v1/model-prices` and clear it with `DELETE /api/v1/model-prices`. The Publish check shows the same kind of estimate for Live and for the draft. That total groups each side's tokens by model before pricing, so it can differ from the figure under one answer by one hundred-millionth of a dollar. A chatflow check prices the same lines the usage write keeps. A harness check prices the route, specialist, and handoff lines stored under the harness name, grouped by model. The Usage page at `/usage` shows those daily tokens and the estimated cost per flow for 7, 30, or 90 days, or a custom range, with flow and model filters. The sidebar entry uses the same view permission as the route. The organization owner can set or clear a model price on that page. [Usage over time](../../docs/how-to/context-and-tokens.md#usage-over-time).
-   **Datasets, evaluators, and evaluations.** The sidebar opens Datasets, Evaluators, and Evaluations (D55). A dataset is example rows, an evaluator is a check, and an evaluation runs a dataset against a chatflow or agentflow. The organization owner can use them, and a role can be granted `datasets:*`, `evaluators:*`, or `evaluations:*`. The flow picker requests only the chatflows and agentflows that role can view. Custom assistants are not evaluated. Deleting rows stays inside the caller's workspace. A grading credential on a new evaluation must be owned by the team. A flow run, including history load and clearing a session, can decrypt a credential that team owns or that was shared into it. A run calls the prediction route on this server when `APP_URL` is unset. A create with a missing dataset, a bad flow list, no flow, an unknown flow, a flow from another team, or a missing name is rejected before a row is saved. A flow list sent as a JSON array is stored as that same JSON string. The evaluation pages do not start that check. A dataset can drive the check in the Publish dialog, which scores each answer with the selected evaluators and shows a pass rate per side. A dataset check also reports passed or failed for the draft against a pass mark. That line blocks Publish only when the flow requires a passing test set (D64). From the message viewer, Add to test set saves one answer and the question immediately before it in the same chat session as a dataset row, with the message, the flow, and the date of the answer (D70). A null session or memory matches only null. A second answer in a row is refused. Saving that answer into the same dataset again keeps the row already stored. The flow and the dataset have to be in the caller's team, and the role needs `datasets:create` or `datasets:update` plus view permission for that flow type. The button is shown for create, or for update together with `datasets:view`. The existing-dataset list needs `datasets:view`. The dialog warns that a real message can contain personal data. With Positive or Negative as the only feedback filter, Add rated answers to test set uses that same question and counts those ratings for the flow over the last 1 to 90 days, then adds one row each in one write (D72). A dry run shows the count and a short preview and writes nothing. A thumbs-up row uses the answer as the expected output. A thumbs-down row leaves the expected output empty, marked needs expected answer, and keeps the rejected answer, the feedback text, the feedback id, and the rating. A message already in the dataset is skipped and does not count toward the limit of 500 new rows. A duplicate found while writing is skipped without failing the other rows. The scan stops after 1,000 ratings or when the limit is full. The cursor is the last rating that call actually read, so a limit that stops partway through a page does not skip the rest of that page. When an older rating remains, the next run starts strictly older than the stored time of that rating, including ratings in the same millisecond. Add writes the ratings from the preview. A write without those ids is rejected, and it cannot send more ids than the limit. If the rating that starts the next page is removed before that page is read, or the cursor rating is removed after it is checked, the scan continues from the stored time of that rating, including microseconds. The cursor sent back is that rating's stored time as text and its id. The next request uses that text whether or not the rating is still there. A cursor is rejected when the id is not a uuid, or when the time is not the stored form the server returns (`YYYY-MM-DD HH:MM:SS` with an optional fraction of up to 6 digits). A time such as `1`, or one with a `T` between the date and the clock, is rejected. A rating that is already gone is not. The dialog stays open while a count, a new dataset, or the add is still running. An exact 1,000 with nothing older is not reported as stopped early. A cursor id that is not a uuid is rejected. SQLite runs these writes one at a time, including into different datasets. Add to test set reads the next sequence number after that same dataset lock. On the Publish check, a row with no expected answer still runs: text, JSON, and numeric evaluators score it, and a model evaluator scores Error without calling the grading model. Reading that check returns the row inputs, expected outputs, and evaluator names only to a caller who can view them. [Evaluations](../../docs/how-to/evaluations.md).
-   **Sign-in and teams.** WorkOS AuthKit sign-in or one local account, teams, users and roles in the app database, and workspace scoping on every route. A harness and its runs belong to the active team: another team's harness is a 404, and a name already used in another team, or a saved harness that is not in a team yet, is a 409 and that canvas is not saved. An external worker refuses a job whose caller team is missing or is not the harness team, and the gateway uses that caller team. Inline and a direct run refuse before a run row is written (D63). [Roles and permissions](../../docs/how-to/roles-and-permissions.md) lists every permission key and the pages and API routes that check it. Publish, draft Save, Review, and Discard draft check `chatflows:update` on `/canvas`, `/harnesscanvas`, and `/etlcanvas`, and `agentflows:update` on the agentflow canvas. The first save of a new flow checks create. Edit Name checks create or update. Use Template needs `templates:marketplace` or `templates:custom` to open the template, and then `agentflows:create` on an agentflow template or `chatflows:create` on a chatflow, harness, or ETL template. `scripts/permission-keys.test.mjs` fails when that table and the keys in the server and the UI differ, or when a permission literal is not in the catalog.
-   **Run traces.** Optional OpenTelemetry traces for chatflow predictions, Multi Agents, Sequential Agents, agentflow runs, and harness runs (`CUTTLELY_OTEL_TRACES`, off by default). One span for the run, a child span per node, and child spans for model and tool calls, with flow id, node type, model name, tool name, tool call id, and token counts. A Multi Agents or Sequential Agents step records one model span per model call, including a model call a nested chain in that step dispatches, and one tool span per tool call from that step. `tool.id` is taken from the model generation when the worker message does not repeat it. An approval finishes that waiting tool span as ok, and a rejection finishes it as error with the message rejected by user, so the trace does not keep a pending span for that call. A tool error that the executor catches marks that step and the run error as well, and the prediction still returns the executor's body. A waiting tool span is ended pending when its continuation record expires or is dropped, when the process is already holding 1,000 of those spans, or when the approval is not saved. The model counts add up to the step total a usage record stores. An approval continues the waiting trace from server-side state keyed by the action, the chat and the flow. That record lasts at most 24 hours, is capped, and is dropped shortly after the resume finishes. The action sent to the client does not carry the trace id. A Condition Agent's model call is a span on that step. The route is the option label stored on the canvas. An edge whose label is not stored is skipped. A model call that does not receive the graph callback list has no model span: the approval prompt in `seekPermissionMessage` on the Sequential Agent node and the Sequential Tool node. A graph node that ends in error marks the run span error too. The approval continuation record is kept in that server process, so a resume on another process or after a restart starts a new trace. With `CUTTLELY_OTEL_TRACES_CONTENT` on, spans add `content.input` and `content.output` (cut at 4,000 characters): the question and the answer, the model prompt and reply, tool arguments and results, analyst SQL when the tool detail still has it, and the analyst run-card preview. A specialist span's content input is the run-card task, at most 200 characters. Off leaves that text out. A chatflow tool span from the model callback sets `tool.name` and does not set `tool.id`. A Multi Agents or Sequential Agents tool span sets `tool.id` when the call has one. The exporter sends only spans started for that run, not spans from the process-wide tracer. A harness run exports harness.run with a child for the route, each specialist, each handoff, each in-process model call, and each tool call. When history saved a run, that span carries `run.id`. That includes a run whose queue worker is another process, and a run that throws after the row was saved. `tokens.input` and `tokens.output` are only on the model spans. A specialist that runs in the agent runtime keeps its token total on the specialist span, covering the whole turn including tool time, and that total is not also a model span. Adding `tokens.input` is the in-process model calls. Add that specialist rollup once to reach the run. The run and each step also carry `tokens.total.input` and `tokens.total.output`, which are rollups and are not summed with model spans that already hold those tokens. A harness tool span has the tool name and status, and an error when the tool fails. An analyst query also has the row count from the run card, and that call's duration. It leaves out the preview and the SQL unless content is on. With content on, the output is that preview, and the SQL is included only when the tool detail still has it. The server builds that tree from the run events, so the runtime process does not load a tracer. A chatflow Harness node nests the tree under the chatflow prediction. A harness canvas draft try and a publish-check replay export nothing. A request for a harness in another team is refused before a span is opened. The span's workspace id is that team's id. Harness tool spans do not carry `node.id` or `node.type`. The local collector example is `examples/otel/collector.yaml`, and the `verify-test` step parses it. Both Compose files pass `CUTTLELY_OTEL_TRACES`, `CUTTLELY_OTEL_TRACES_ENDPOINT`, `CUTTLELY_OTEL_TRACES_PROTOCOL`, `CUTTLELY_OTEL_TRACES_CONTENT`, and `METRICS_SERVICE_NAME` from `.env`. A blank `METRICS_SERVICE_NAME` is unset, so traces use `cuttlely` and the admin Service name field stays editable. `docker/docker-compose-queue-source.yml` passes those same variables, blank meaning unset, on the server and the worker, and maps `host.docker.internal` with `host-gateway`. [Run traces](../../docs/how-to/observability.md).
-   **Admin panel.** Admin > Server settings holds every server setting with help text, a review step, restart to apply, safe boot back to the last good settings, History, and a guided sign-in setup. Admin > Logs shows recent server log files from `LOG_PATH` for the organization owner or a role with `logs:view`, with level and time filters. Presets send a range token the server expands on its own clock. Custom sends the browser's `YYYY-MM-DD-HH` stamps, which the server reads as its own local hours. The page returns one contiguous recent section: a newer file that was read in full can be followed by the next older file, and once a file is tailed, older files are not added. Redaction runs on the joined text, so a secret that spans lines becomes `[secret hidden]`. A capped tail keeps lines only from the first log record (`YYYY-MM-DD HH:mm:ss [LEVEL]:`, and an error record is a record start). Lines before that record, including a window with no record start, are replaced with `[earlier output cut]`. An API key cannot read them. Login activity stays closed (D56). `CUTTLELY_SECRETKEY_OVERWRITE`, `CUTTLELY_FILE_SIZE_LIMIT` and `DISABLE_CUTTLELY_TELEMETRY` are compatibility aliases for the existing variables. When both names are set, the `CUTTLELY_` name is used, except the encryption key: different values refuse to start. `METRICS_PREFIX` is optional and unset output matches the metric names published before it.
-   **First ten minutes.** Install, first account, and Try the demo, which opens a made-up customer care team on the person's own model key with its chat open: a customer specialist (support desk database), an operations specialist (warehouse and carrier scans) and a policy specialist (the written Service Recovery Policy and its remedy table, sent after operations), each in its own folder with its own data and Python tools, with Harness Prime writing the decision, the reply, the actions and the evidence. The data and tools are in `samples/demo/customer-care`. The bakery team is the quickstart on the same card. The README section "Your first 10 minutes" walks through it.
-   **Install and deploy.** Docker Compose (SQLite, one container), `npx cuttlely` (the same image, through the `cuttlely` launcher), from source, and a Render Blueprint (Docker web service, Postgres, disk). The server serves the built UI from `packages/server/dist/ui`, falling back to a newer `packages/ui/build` or a linked UI package. A production install does not install the UI package's libraries. `pnpm dev` still serves the UI on port 8080. The image includes Chromium and the IP geolocation database. `INCLUDE_BROWSER=0` builds one without Chromium; Puppeteer and Playwright document loaders in that image fail with `this image has no browser`. The agent runtime's browser tool also cannot browse there: it returns success: false, and the server keeps running. `CUTTLELY_OMIT_GEOIP=true` leaves the geolocation database out; audit events then have no country and no region. The two arguments are independent, the defaults keep both, and the published image is still the default build. `INCLUDE_NODE_PACKS=0` leaves optional node packs out of the image (`/etc/cuttlely/no-node-packs`); the default `1` keeps them, including the vector store pack, the tools and MCP pack, the caches and memory pack, and the legacy completion and chain pack. It is independent of the browser and geolocation arguments. `docs/how-to/from-source.md` covers the dev server, the tests and `pnpm verify`. `@cuttlely/chat` is the embeddable chat widget, also served by the server at `/embed/chat.js`.
-   **Releases.** `pnpm release` cuts a release from a clean `main`, drafts by default, and pushes the image or publishes the GitHub release only on a flag. `pnpm release X.Y.Z --npm` publishes the npm packages from that annotated tag after the image and the GitHub release are public. v1.0.3 is the latest release: the tag, the published GitHub release, the image `ghcr.io/cuttlely/cuttlely` at `1.0.3` and `latest`, and `cuttlely` and `@cuttlely/chat` 1.0.3 on npm all come from that tag. `CHANGELOG.md` dates it 2026-10-13. v1.0.2, the dependency security release, is the previous tag, and `CHANGELOG.md` dates that release 2026-10-11. The npm 1.0.0 packages were built from a commit after the v1.0.0 tag and are deprecated in favor of 1.0.1. The full `pnpm verify` tests upgrades from a fixture made from the v1.0.3 tag.
-   **Graceful shutdown.** On SIGTERM or SIGINT the server stops taking new requests (`503` with `Retry-After`) and lets running answers and streams finish for up to 25 seconds (`CUTTLELY_DRAIN_TIMEOUT_MS`). The Compose files give the container 35 seconds to stop.
-   **File links in Agent answers.** A file an Agent card links in its answer opens for 15 minutes without the flow's API key: the link carries an expiry and an HMAC over the organization, flow, chat and file name, keyed from the server's own secret. A changed or expired link falls back to the key or session checks.
-   **Provider rate limits.** Chat models and LLMs make at most 3 tries and start no new try after 20 seconds. A provider that keeps answering 429 is reported as `429` with `Retry-After` (the provider's wait, else 30 seconds), and a stream ends with an `error` event carrying `status`, `code` `RATE_LIMITED` and `retryAfter`. An out-of-credit 429 still fails as `500`.
-   **No call home.** A default install reaches only services an operator or a flow set up. `SECURITY.md` lists every outbound host and how to turn it off.
-   **Website product videos.** Each card under "Tools your teams use" on the home page has a short video of a real recording: a poster first, a muted loop that plays only while the card is on screen, and a narrated version with captions in a dialog. Nothing autoplays with reduced motion, on small screens, or when `navigator.connection.saveData` is set. A Save-Data request header alone does not opt out, because the site is static. The hero video follows the same rule. A play button is on the hero and on each tile loop while that preview is silent. The hero button is centred. The tile button is smaller than the hero button and sits just left of the product name in the preview, so the title and the Watch with sound chip stay clear. Reduced motion, a narrow screen and Save-Data still show the poster with that button. Activating the button or the preview starts the video from the beginning with sound, turns the loop off and shows the player controls. The hero plays in place and, when that playback ends, returns to the silent preview or the poster with the button. When autoplay is off, that return detaches the sources and loads the empty element so the poster paints, and the next play puts the sources back without a second fetch. Starting one video pauses the others. A hero that was playing with sound returns to the silent preview, button included, and a volume the visitor set is left as it is. While a narration is playing, on-screen previews stay paused even if a download finishes or they scroll back into view. Scrolling that video off screen ends the sound session, including when autoplay is off. Closing a tile dialog, the hero narration ending, a media error on that video, or the play being refused resumes on-screen silent previews the loading queue has already started, and does not fetch the ones still waiting, when autoplay is allowed. An error on any other video leaves the session running. With autoplay off, a refused hero play returns the poster. A refused dialog play ends the narration and leaves its sources attached, so the next open plays the file. A tile opens the narrated dialog from the beginning with sound every time, and closing the dialog pauses it. The hero and the tile loops start downloading when they are within about a viewport of the screen, two at a time and in page order. A loop that is already half on screen moves ahead of the ones that are only nearby, and it plays when its download starts, still with at most two downloads in flight. A loop that has already fetched is not loaded again, so playback is not sent back to the start. A slot is freed when the loop can play through, when the video reports an error, when the last candidate fails, or when the element is already out of sources or fully buffered as the slot opens. A download that only stalls keeps its slot. A frozen page aborts the fetch without those events. Once the page is visible again, every held loop that is not yet fully buffered is loaded again, whether it was playing or had scrolled off screen, and the playhead is put back once that time is seekable, retrying a seek that did not stick. A second freeze before that seek has landed keeps the original time. A playhead the visitor has moved since the reload is left alone, including a seek back to the start. A second freeze before the first metadata event does not add another listener. Once that metadata arrives, a restore that started at the beginning is finished, and a later freeze reads the playhead as it is. A fully buffered loop is left as it is. Safari and Firefox do not fire resume, so a socket aborted while hidden, and not restored from the back-forward cache, is restarted only when that hidden resume was already seen and the page becomes visible later. Returning to a visible tab does not restart a download on its own, because that would abort one that is still healthy. ## How it is checked

-   `pnpm verify` on Node 24 is the merge gate (DECISIONS D27). The full run has 26 steps. `pnpm verify --help` lists every step and the `--fast` set. The `canvas-actions` step opens the chatflow and workflow canvases in a browser, duplicates a card, deletes the copy, and closes the settings panel with the button and with Escape. It also drags a card to the top edge, and it hovers an unselected card and clicks Duplicate and Delete with the row above the card and below it. Backspace removes a selected card when the panel is closed, and Backspace in a panel field only edits that field. Backspace on a connected card marks the canvas unsaved. Deleting one of two lines from the same card clears only that line's field. A workflow mention span is removed whole, and a longer id's span stays. The saved flow for the chatflow, workflow, harness, and pipeline canvases has no dangling reference after a button delete or a keyboard delete (D60). A docs-only change uses `--fast`. The `boundaries` step fails a new import across a zone, or a new file under an inherited path that is not assigned to a subsystem. A recorded line that is no longer in the tree fails until `node scripts/check-boundaries.mjs --update` shrinks the list. The typecheck step runs in both modes: components, the versioning core, and the server, plus `tsc --noEmit` for `packages/api-documentation`. The `versioning` step runs the versioning core tests.
-   `packages/components/nodes/load-coverage.test.ts` loads every catalog node and every credential class, checks the description fields, and calls `init` only when that call stays on the machine. Without coverage instrumentation, module evaluation (node and credential `require`, plus those inits) must finish in under 20 seconds. The whole test, including a cold ts-jest compile, must finish in under 150 seconds. The file's Jest timeout is 180 seconds. The `unit` step of `pnpm verify` (full and `--fast`) runs this file with `--coverage=false`, and that is the run that enforces both limits. No job in `.github/workflows/` runs it without coverage. The build job's `pnpm test:coverage` still loads every class and still fails when a problem is recorded, skips only the time assertions, and prints the elapsed time. `scripts/build-module-catalog.mjs` writes the support tier (`core`, `supported`, `legacy`, `hidden`) on each catalog row.
-   `node scripts/health-report.mjs` prints code lines per zone, production dependencies, boundary edge counts from `scripts/check-boundaries.mjs`, and how many catalog nodes have a unit test. Node CI appends it to the build job summary, and the Docker job adds the image size (`--image cuttlely`). The report exits 0. Those CI steps do not fail the job. The 2026-10-11 figures are in [docs/reference/health-baseline.md](../../docs/reference/health-baseline.md).
-   `pnpm harness:check` (`node packages/harness/check.mjs`) and `pnpm etl:check` (`node packages/etl/check.mjs`) are offline checks with no model key and no network. `node harness/check.mjs` and `node etl/check.mjs` still run them for one release.
-   Analyst paging at a raised row cap is checked in `scripts/analyst-store.test.mjs`: a 600-row table with a cap of 250 is paged to the end, each row appears once, and the run card count matches the page. A full cap still allows a jump to page N. After a short page the line names the row total and says show more, with no page count, and a jump past the next page is refused. A keyset or offset result states a page count only after a length pass shows the walk matches a full cap on every page; the pass bounds text, varchar, and name by UTF-8 bytes, character(n) by the detoasted padded byte length, dates by 128 characters, and a json scalar or object by at least 24. A JSON array has no bound. A type with no bound leaves the walk unknown. Until the walk matches, a jump other than the next page or page 1 is refused. A seeded property check covers a few thousand random page sequences in buffer, keyset, and offset, including pages the budget cuts short. The same file checks that a host row cap or query timeout of 0, a negative number, or a non-numeric value uses the default and warns once, and that a query timeout under 1 second is raised to 1 second. A reused Postgres session keeps the hard-maximum client backstop, so a later longer statement is not cut by the first call's read timeout. A node row cap between 0 and 1 is 1 row.
-   The `smoke` step boots the built server; the `upgrade` step starts it on data from an older release; the `safeboot` step checks the settings rollback.
-   The daily scheduled CI run on `main` also runs `pnpm test:queue-abort`, an end-to-end queue-mode abort test against a Redis service.
-   Workflows in `.github/workflows/` are the CI definition, but they are not the merge gate. See [OPEN.md](./OPEN.md). Their `pnpm/action-setup` steps take the pnpm version from `packageManager` in `package.json`; a separate `version` input stops the step when the two disagree.
-   `pnpm audit --prod` and `pnpm audit` report no critical advisory. Three high ones are left, and none has a fixed release. `extract-zip` (two advisories) is in Puppeteer's browser download, which Cuttlely skips (`PUPPETEER_SKIP_DOWNLOAD`), so that code does not run. `braces` 3.0.3 is the latest release and is still in the vulnerable range; it arrives through the command-line file matcher and through dev tooling, and request handling does not pass input to it. `expr-eval` is not installed: the older community package that depended on it is gone, and that package has no fixed release.
-   A green `pnpm verify` is not a real-model run. Harness and analyst behaviour that depends on a model needs a live run with a real credential before it is called done (MEMORY).
