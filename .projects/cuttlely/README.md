# Cuttlely project notes

These notes let a new contributor, or an AI agent running the `take-over` skill, pick up Cuttlely where the work stands instead of starting from zero. They describe the code on `main`, the decisions behind it, the work that is open, and how to check and ship a change.

Cuttlely is the open-source agent platform for applications. It gives applications agent teams (harnesses) that apps call through the API and people chat with, plus the knowledge pipelines (ETL), chatflows and agentflows those teams use. Everything runs on infrastructure the operator controls. The user-facing story is in the root [README](../../README.md) and the [docs index](../../docs/README.md).

## How to resume

1. Read [STATUS.md](./STATUS.md), then [OPEN.md](./OPEN.md), then the open issues: `gh issue list -R cuttlely/cuttlely`. Also check open pull requests (`gh pr list -R cuttlely/cuttlely`) so you do not redo work that is already in review.
2. Read [DECISIONS.md](./DECISIONS.md) before changing architecture. Those decisions are settled. To change one, add a new entry with the reason; do not quietly redo it.
3. Pick the next task from [PLAN.md](./PLAN.md) or an open issue that is not blocked on a maintainer decision.
4. Work on a branch, one change per pull request, as [RUNBOOK.md](./RUNBOOK.md) describes. Before a pull request, run `pnpm verify` on Node 24 on the exact head (`pnpm verify --fast` for a docs-only change).
5. Follow [MEMORY.md](./MEMORY.md) for conventions and lessons.
6. When project state changes, update these files in the same pull request. The `refresh-project-handoff` skill checks them against git once before a push or a pull request.

## Rules for these notes

These files are public. Keep them that way:

-   No secrets, tokens, keys, connection strings or `.env` values. Name an environment variable; never write its value.
-   No personal names, personal accounts, private hostnames, internal links or machine-specific paths. Write paths relative to the repository root.
-   No customer data. Examples and fixtures use made-up data.
-   No business notes. These files describe the code and how to work on it.
-   Link an issue instead of restating its status, so the notes do not go stale when it closes.

Inbound API and SDK authorization is in `packages/server/src/services/accessKeys/`; the stable `apikey` principal owns credential, resource, quota and report-receipt rows. The public [Access keys reference](../../docs/reference/access-keys.md) and `scripts/access-keys-migration-report.cjs` cover migration and rollout. Read that reference before changing inbound authorization. `packages/server/src/settings/accessRollout.ts` resolves the service-wide host/admin/default mode for the instance-operator Server settings control; `scripts/access-rollout-admin.test.cjs` exercises it through actual application routes. Model-provider credentials and public share links remain separate.

`architecture/boundaries.json` assigns inbound access-key code and the existing key-management seam to the Access keys subsystem. Adapter crossings to flow/runtime/storage code are recorded with an explicit reason; `node scripts/check-boundaries.mjs` checks that boundary.

`packages/server/src/identity/instanceOperator.ts` checks host-backed service authority independently of tenant roles and binds it to the actual database connection. `operatorBinding.ts` stores private Active/Disabled authority and reads verified historical host bindings. `settings/operator-claim.ts` provides explicit panel claim, transfer/revoke and distinct host-proof recovery/rebind. Only actual host bindings grandfather; legacy installs claim with one host-log code. The user CLI is emergency recovery. Any defined override disables panel lifecycle. Host onboarding, database changes and recovery are in [Instance operator](../../docs/how-to/instance-operator.md).

Ordinary-login save protection is in `settings/service.ts` and the persisted readiness adapter in `identity/authenticationState.ts`. `scripts/settings-no-way-in.test.cjs` covers actual application/SQLite behavior, and `scripts/settings-workos-warning.test.cjs` composes fresh WorkOS upgrade inference, legacy links and HTTP transition checks; [D116](./DECISIONS.md#d116-settings-login-safety-validates-transitions-against-established-ordinary-login) records the transition-only contract, separate from provider activation and operator authority.
