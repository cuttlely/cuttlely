# Cuttlely project notes

These notes let a new contributor, or an AI agent running the `take-over` skill, pick up Cuttlely where the work stands instead of starting from zero. They describe the code on `main`, the decisions behind it, the work that is open, and how to check and ship a change.

Cuttlely is the open-source agent platform for applications. It gives applications agent teams (harnesses) that apps call through the API and people chat with, plus the knowledge pipelines (ETL), chatflows and agentflows those teams use. Everything runs on infrastructure the operator controls. The user-facing story is in the root [README](../../README.md) and the [docs index](../../docs/README.md).

## How to resume

1. Read [STATUS.md](./STATUS.md), then [OPEN.md](./OPEN.md), then the open issues: `gh issue list -R cuttlely/cuttlely`. Also check open pull requests (`gh pr list -R cuttlely/cuttlely`) so you do not redo work that is already in review.
2. Read [DECISIONS.md](./DECISIONS.md) before changing architecture. Those decisions are settled. To change one, add a new entry with the reason; do not quietly redo it.
3. Pick the next task from [PLAN.md](./PLAN.md) or an open issue that is not blocked on a maintainer decision.
4. Work on a branch, one change per pull request, as [RUNBOOK.md](./RUNBOOK.md) describes. Before a pull request, run `pnpm verify` on Node 24 on the exact head (`pnpm verify --fast` for a docs-only change).
5. Follow [MEMORY.md](./MEMORY.md) for conventions and lessons.
6. When project state changes, update these files in the same pull request. The `refresh-project-handoff` skill checks them against git once before a push or a pull request.

## Rules for these notes

These files are public. Keep them that way:

-   No secrets, tokens, keys, connection strings or `.env` values. Name an environment variable; never write its value.
-   No personal names, personal accounts, private hostnames, internal links or machine-specific paths. Write paths relative to the repository root.
-   No customer data. Examples and fixtures use made-up data.
-   No business notes. These files describe the code and how to work on it.
-   Link an issue instead of restating its status, so the notes do not go stale when it closes.
