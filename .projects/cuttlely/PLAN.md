## Kraken 2.0 development

The `Kraken` branch tracks the [native runtime proposal](https://github.com/cuttlely/cuttlely/issues/594). The [canary and rollback guide](../../docs/reference/kraken-native-runtime.md) covers per-team selection, queue compatibility, saved credential bindings and operator checks. Both router and agent mode use the admitted engine. Preflight reports unsupported capabilities by specialist.

An operator can opt a native admission into on-demand role checks for a published mixed team. A supported role can run on the unchanged canvas. Selecting a shell or interactive browser role fails the turn before its dispatch. A code-enabled role can sum, count, sort, or find the extrema of a bounded literal integer list when it has neither of those grants. Queued runs retain the policy and saved team revision across worker replacement. Strict admission remains the default, and export preflight still identifies every saved capability that needs the bundled runtime. [Operator procedure](../../docs/reference/kraken-native-runtime.md#trying-a-mixed-team-on-demand)

Native specialists can use saved Markdown playbooks, Calculator, Current Date Time, supported Pinecone retrievers and SerpAPI search, caller-supplied public source pages, the packaged Ops MCP action and guarded PostgreSQL Analyst cards. The registered workspace MCP status contract has Streamable HTTP and SSE coverage. Native file specialists have scoped uploads, patching, search and downloadable outputs on compatible Linux workers. Prompt history, search, private files and Analyst follow-ups use the admitted caller and canvas generation. Previously queued exchanges can supply ownership evidence for existing installations.

A three-specialist fixture exercises both execution modes, including a partial failure after a file write. The native runtime preserves tool results for JSON-only providers and can use an uploaded CSV as the source of a downloadable table and chart. An explicit database request retains its query requirement. Assigned playbooks can expand the admitted session and read immutable companion files bound to the saved canvas.

The public transport fixtures check the widget’s streamed result, anonymous session continuation, the origin policy and an HMAC-signed webhook that calls a saved team. Verified CSV reports can also return PDF, Word and Excel downloads. A published canvas can use its generation-bound playbook companion on a replacement worker. A playbook turn rechecks the saved revision before it streams or returns an answer. The offline export check identifies assignments that need installation evidence. An unbound search card reports its credential error at the same stage as the released tool when the deployment has no host search key.

The optional native image builds from a source archive without the bundled runtime. The package fixtures cover the normal launcher, independent workers, empty-disk recovery and rollback. New calls carry a durable tool dispatch receipt so a worker loss can surface an uncertain result. See the canary guide for the preflight command and per-team acceptance checks.

Native runs record the winning specialist model and retain provider-reported input, output and cached-token counts. A single model streams text immediately. When two models can compete for the same call, the client receives the selected answer after the race finishes.

On `/prediction`, ordinary agent answers preserve the released stream order when the final event precedes the last text fragment. Canvas chat and the team view display the answer once. For verified output, the endpoint sends attachment bytes before the answer names the file. An incomplete source result or missing bytes produce a stream error before any file is announced. Named runs check the required attachments before delivering their existing sequence of answer events followed by files.

For published agent-mode teams with direct chat models, the full build can record a bundled specialist’s progress against the active PostgreSQL turn during rollback. This covers model-only specialists and the packaged read-only Ops action. The latter resolves its installed script from the package when the worker starts in another directory. Other team configurations still need a rollback rehearsal.

PostgreSQL recovery checks now exercise loss of the coordinator while ordinary queries still succeed, standalone worker replacement, and a surviving worker that finishes an asynchronous run after the accepting API stops. The original caller can poll for the stored answer or the expired worker's unconfirmed action. Two API replicas observing one due schedule and an external worker produced one tool response and one run history entry after replacement. The runtime guide maps each v1.7.15 vendor patch to a verification fixture or outstanding comparison.

The Chief of Staff template retrieves its embedded document in both modes. The Research template now connects its Custom Retriever to a local sample store. An older Research canvas with an empty vector-store input identifies that missing binding. Scoped prediction checks cover the returned answer, source placement and denied keys for both teams. A simulated accounting outage verifies that a completed PostgreSQL job can recover its result and token buckets once, even after the accepting API exits.

History retention keeps live turns and accepted results awaiting accounting in addition to the 100 settled results per team. A replacement worker retries accounting after transient database errors. The pressure fixture checks an older admission against 101 later completions and verifies that a blocked workspace still allows a different workspace to settle.

PostgreSQL queue polling reads the job status and its ordered public events from the same snapshot. At the wait deadline the queue checks the current job under the same lock used to finish it. A job that completed first delivers its final events once. If the job is still active, the waiter requests cancellation and returns a timeout.

The local Custom Retriever preserves all three saved output selections. AI Builder can reconstruct the Research example with the intended output and source metadata. Public prediction fixtures exercise imported and generated teams on SQLite and after replacing a PostgreSQL application host.

Release acceptance requires matched cold and warm authenticated team runs against tagged v1.7.15. Compare 1, 8 and 32 concurrent requests at a fixed worker count, then 32 requests on 1, 2 and 4 workers. Each matched configuration must meet the tagged end-to-end p95 and successful completion rate with correct, owned answers and no dropped or duplicate work. Record admission and API ping latency, errors, timeouts and variation across balanced repetitions. [Concurrency acceptance criteria](../../docs/reference/kraken-native-runtime.md#concurrency-acceptance-for-a-release)

Full team parity and retirement of the bundled runtime remain open. General shell, code execution and interactive browser grants, other MCP actions, operator-supplied runtime dependencies and historical conversations without reliable ownership need further work. Keep the full installation available for teams that depend on those features.

## Next concrete tasks

PostgreSQL application storage includes the verified SQLite primary copy, ETL and vector stores, agent teams, settings and credentials, uploads, and current and historical flow versions. The [operator guide](../../docs/how-to/postgres-side-stores.md) covers fresh installs, existing PostgreSQL installs, SQLite migration, optional S3-compatible file storage, host-file dependencies and rollback. [PostgreSQL consolidation #516](https://github.com/cuttlely/cuttlely/issues/516)

The storage upgrade card asks for one confirmation covering the backup and the displayed PostgreSQL space requirement. The release gate exercises the primary copy, side-store migration and empty-disk replacement. The replacement worker explicitly confirms that its credential-backed query and attachment read completed. The earlier worker exit-code check could pass before the query ran. The crash fixture covers concurrent session writers, transcript messages saved through the gateway, settings saved through the runtime and notes saved by the memory tool. It verifies that a rejected PostgreSQL commit reaches the gateway caller and leaves no message queued in memory. The image sets read and traversal permissions for arbitrary UIDs when built from a private checkout. Its entrypoint provides an ephemeral home and log directory and supplies the shell for UIDs without a passwd entry. The startup import probe runs in a disposable runtime home so its default prompt cannot prevent a fresh PostgreSQL cutover. Docker CI starts the packaged service and checks the storage phase before and after replacing its writable filesystem. Files produced by code execution in local workspaces are outside the recovery guarantee. The recovery boundary is a successful Cuttlely or runtime save. After direct shell edits on ephemeral disks, the replacement restores the last committed settings. [Replacement fixture](../../scripts/storage-replacement.test.mjs)

The server and workers verify the storage selection before writing application data. When a legacy installation cannot reach its host database at startup, the health endpoint returns HTTP 503 and identifies the outage. The [safe boot check](../../scripts/safeboot-check.mjs) covers that recovery path.

The storage upgrade includes regular local profile prompts in its verified PostgreSQL snapshot. Each new runtime disk restores that snapshot once. Later prompt edits remain local.

Exact matches and the two rebuildable skill metadata files appear as temporary. The storage recovery suite covers changed, custom and linked files, profiles that opt out of bundled skills, and missing catalog entries.

The [disk storage inventory](../../docs/reference/disk-storage-inventory.md) maps application, workflow and runtime SQLite files, server settings and credentials to their writers and retention requirements. Compare a private metadata inventory before and after each overall upgrade test. The ETL store gate queues already-admitted writes before draining and allows subsequent calls after a failed statement. A regression covers both behaviors.

-   **Resilient save queue (done).** Landed on main as `52e29426` ([#462](https://github.com/cuttlely/cuttlely/pull/462)) from `fix/save-queue`. It shares a single-flight queue between both canvases. Draft writes replay only after a missing response and a status check; HTTP write responses never replay. Landed detection requires present draft metadata, a changed hash, the current account, an updated time between the first send minus two minutes and the last settle plus two minutes, and equal content for non-file canvases. Later recovery requires the captured draft base to remain unchanged. Non-file bursts continue through no-response reads; file canvases and HTTP read errors wait. Live writes reconcile parsed canvas, name, file names, and update time; a guarded action sends at most one PUT. Confirmed older writes run before a newer pending snapshot. Creation uses one POST, waits for a known save mode, and turns a later queued Save into a draft or Live update on the returned id; an unavailable post-create status read gets its own Retry notice. Internal name and starter-question updates stay serialized without replacing a user snapshot or clearing first-save questions early. An unanswered inline name remains available to the next canvas Save. Busy state holds inline name Save and Publish until the queue is idle. Session refresh is single-attempt and does not reissue writes. The optional `Idempotency-Key` header and `expectedUpdatedDate` comparison remain deferred.
