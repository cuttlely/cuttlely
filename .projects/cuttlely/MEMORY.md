# Memory

Conventions, do and don't, and lessons a newcomer would otherwise relearn. Add a lesson only when one was actually learned.

## Conventions

-   Harness runtime code is plain Node ESM in `packages/harness` (`@cuttlely/harness`). Analyst storage, paging, the analyst database check, the SQLite worker, tool status, and the stream lease live in `packages/harness/runtime/`. `harness/` re-exports the package for one release. ETL runtime code is plain Node ESM in `packages/etl` (`@cuttlely/etl`), loaded from the CommonJS server with a real dynamic import. `etl/` re-exports that package for one release. Canvas nodes are TypeScript under `packages/components/nodes/`. Bump a node's `version` when its inputs change.
-   The canvas label is Harness Prime; the saved node name stays `harnessChief`, type `HarnessChief`. Template card titles are Title Case, but harness record names and a chatflow's `harnessName` stay the runtime id (`upload`, `field-team`, `calculator`).
-   Runtime profile names: harness `<harness>`, agent-loop specialist `<harness>--<specialist>`. Session key `{harness}:{chatId}`. A specialist's runtime toolset for an MCP server is the server name (`analyst`), not `mcp-<name>`.
-   A chatflow MCP endpoint's `initialize` server name is `cuttlely-<slug>` from the flow name (lowercase `[a-z0-9-]`, at most 64 characters), or `cuttlely` when the name has no usable slug. It is not the configured tool name.
-   `RateLimiterManager.getRateLimiter()` reads `req.params.id`. The MCP route is `/:chatflowId`, so MCP POST must call `getRateLimiterById(req.params.chatflowId)` or the flow's Rate Limit never applies.
-   Every harness behaviour change gets a case in `packages/harness/check.mjs` with mocked runtime and model calls, runnable without a build, a key or the network. The same goes for ETL and `packages/etl/check.mjs`.
-   A harness card opens `/harnesses/:name` (runs and a prompt box); the canvas is `/harnesscanvas/:id`. The canvas chat and Try it post to `POST /api/v1/internal-prediction/:chatflowId`, which runs the draft when one exists and refuses every API key (`API_KEY_BLACKLIST_URLS`, and the controller itself). `POST /api/v1/harnesses/:slug/runs` stays on the published roster.
-   Express routes ignore letter case and route `/api/v1//x` like `/api/v1/x`, so any allow or deny list of request paths (the API gate lists, the session-attach skip list, the run counter) compares in lower case with repeated slashes collapsed (`normalizeApiPath` in `packages/server/src/identity/apiGate.ts`). A route test for a refused path also sends it capitalised, in mixed case, and with a doubled slash, through one `/api/v1` router mounted as in `routes/index.ts`.
-   Read harness names from parsed JSON, never with a text search: a key written as `harness\u004eame` parses to `harnessName` and would slip past a substring check. Check the type too: a regex test or a template string turns `["payroll"]` into `payroll`, so a name check that is not `typeof name === 'string'` lets a list through.
-   `req.originalUrl` is the encoded path; `sanitizeMiddleware` decodes `req.url` before routing. Match a route by `req.baseUrl + req.path`, the path the router used.
-   A harness route that names a harness has `requireHarnessAccess()` after the role gate (`packages/server/src/services/harnesses/apiAccess.ts`). An API key needs the harness on `apikey.harnesses`; a person does not. A new run route gets the same middleware, a start route also gets `harnessRunRateLimit('start')` and a read `harnessRunRateLimit('read')`, and a run read passes `callerApiKeyId(req)` so a key sees only its own runs. A route that reads or writes one chatflow row gets `requireHarnessCanvasAccess()`, and a route test that sends an API key to one installs `setHarnessFlowLookup`. A new save path passes `caller` to `saveChatflow`, `updateChatflow` or `saveDraft`, so `validateReferencedHarnesses` checks the key's list (D91). Write a harness name to a log or audit row through `safeHarnessName`. A schedule write checks a run key and refuses an API key in the controller, because a schedule runs as its owner (D92).
-   Every harness call names its caller (D91). Pass `flowOptions.harnessCaller` to `runHarness` and `runQueuedHarness`, `caller` to `syncHarnessFromFlow`, `assertRunRequest`, `startRun` and `startCheck`, and `harnessCaller` to `executeFlow`. Build it with `harnessCallerFor(req)` on a route, `flowHarnessCaller(apikeyid, workspaceId)` for a flow no person is signed in to, or `{ via: 'session' }` where the API gate only lets in a person. Leaving it out is a refusal, not a default. Tests in `packages/harness/check.mjs` get a session caller from `withServerContext` and the `syncHarnessFromFlow` wrapper.
-   A pipeline canvas (`/etlcanvas/:id`) saves to a draft. Scheduled runs, `POST /api/v1/etl/pipelines/:id/runs`, and a full rebuild read the published pipeline version until Publish. Preview (`POST /api/v1/etl/pipelines/:id/preview`) runs the canvas and does not write the store. The Publish dialog lists the structural diff and does not mount the question check.
-   Canvas permissions live in `packages/ui/src/views/canvas/canvasSavePermission.js`. Publish, a draft save, and the stale-draft Review and Discard buttons check `chatflows:update` or `agentflows:update`. The first save of a new flow checks create. Edit Name, and Save while drafts are off, check create or update because `PUT /api/v1/chatflows/:id` accepts either.
-   Use Template uses `templateUsePermission` in `packages/ui/src/views/marketplaces/templateUsePermission.js` for the button. Opening `/marketplace/:id` or `/v2/marketplace/:id` still requires `templates:marketplace` or `templates:custom`. The button then checks `agentflows:create` on an agentflow template and `chatflows:create` on a chatflow, harness, or ETL template. Permission keys use a colon.
-   Run history stores the same `trace` object the chat renders (`packages/harness/trace.mjs`), and every view uses `HarnessRunTrace`. A specialist model label is the node label and model name, never a credential id.
-   `teamAccess` and `sessionFor` set owner only from the active membership in the active workspace's organization. The session's `isOrganizationAdmin` and `activeOrganizationId` follow that team. An owner role in another organization does not pass an owner check on this team.
-   Workspace queries use `getWorkspaceSearchOptions` from `packages/server/src/identity/workspaceScope.ts`; a missing workspace id is a 400, never "list everything". A harness file is one name per install. Reads compare `workspaceId` with the caller's active team and return 404 when it differs. A save of a name that already belongs to another team, or of a file that has no resolved team, returns 409 and leaves the file as it is. An external queue job keeps the caller's team and is refused before a run row when that team is missing or differs; the gateway compares the caller, not the file (D63).
-   A shipped migration is never edited. New tables go in a later migration whose down drops them. MySQL and MariaDB need unique foreign-key names (`fk_<table>_<column>`) and matching column types and collations. `AddSessionSeen` is `1798000000000` and `AddLocalDirectory` is `1799000000000`, so session activity is added before the local-directory columns.
-   The Usage page (`/usage`) is shown for `chatflows:view` or `agentflows:view`. The price editor on that page is the organization owner only, the same check as `/api/v1/model-prices`. The Flow and Model filters are native selects, and their labels stay shrunk so the label does not cover the selected value. The price editor has no select.
-   Model-list `input_cost` and `output_cost` are US dollars per token. `model_price_override` and `GET /api/v1/model-prices` are US dollars per million tokens. The evaluation cost calculator multiplies a per-thousand-token rate by tokens divided by 1,000. A usage estimate counts hundred-millionths of a dollar in integers, so a half unit rounds up. A Publish check answer is priced on its own. The side total groups those token lines by model and prices each model once, so it can differ from the sum of the answers by one hundred-millionth of a dollar. A chatflow check prices the callback sink the usage write keeps, and a tracer row with token counts and no model name is not a line. A harness check prices the route, specialist, and handoff lines stored under the harness name, grouped by model. A harness model string is the node label, a middle dot, and the catalog id. An override on that full string wins; otherwise the price is the catalog id. MySQL and MariaDB keep the model name on `utf8mb4_bin` for both `model_price_override` and `token_usage_day`. A missing price is `no price`, not zero.
-   Code comments explain the reason in words. They do not cite issue or pull request numbers.
-   User-facing text has no git words (Draft, Publish, Roll back, Keep a copy in GitHub). The promote and GitHub card messages are tested for this.
-   A harness publish check reads full user turns from the session messages table (newest distinct, same caps as chat questions). Secrets are redacted, then the text is cut at 2,000 characters with no preview ellipsis. `takeAnalystResults` claims only the chat id it is given. Each side uses the canvas try (`replay: true` on `runHarness`, its own try id). The try and each specialist profile are closed before those directories are removed. A directory that is still there is logged once and removed on the next start, and a saved harness is left in place. That path writes no run history, no session turns, and drops analyst capture for the check's chat id only. Route, specialist, and handoff tokens are the report total. A harness accepts `datasetId`. Those rows are asked on both rosters in the saved order. Sending `questions` or `count` with it is 400. SQL refusal stays on the try profile. A specialist with Shell, Browser, Code execution, or Files is a risky step. Harness Prime is not.
-   Add to test set, on an answer in the message viewer, writes one dataset row from that answer. The question is the message immediately before that answer in the same chat session (the same chat, memory, and session; a null session or memory matches only null), and it has to be a non-empty user message. A second answer in a row is refused. Provenance columns on `dataset_row` stay null for a row typed in or uploaded. The same message and dataset return the existing row. `POST /api/v1/datasets/rows/from-message` accepts `datasets:create` or `datasets:update` and also checks view permission for the flow type. The button is shown for create, or for update together with `datasets:view`. The existing-dataset list needs `datasets:view`. Create without that view still gets a new dataset (D70). `POST /api/v1/datasets/rows/from-ratings` uses that same question lookup for one rating, `THUMBS_UP` or `THUMBS_DOWN`, over the last 1 to 90 days. A dry run writes nothing. The rows are saved in one write. A thumbs-up row expects the answer. A thumbs-down row leaves the expected answer empty, sets `needsExpectedAnswer`, and stores the rejected answer and feedback text. A message already in the dataset is skipped and does not use up the limit of 500. A duplicate found while writing is skipped without failing the other rows. The scan stops after 1,000 ratings or when the limit is full. The cursor is the last rating that call actually read, so a limit that stops partway through a page does not skip the rest of that page. When an older rating remains, the next run starts strictly older than the stored time of that rating, including ratings in the same millisecond. Add writes the ratings from the preview, so one that arrives after the count is not written in that add. A write without those ids is rejected, and it cannot send more ids than the limit. A cursor sent with those ids is still checked, and a bad one is rejected. A good one does not choose the rows. If the rating that starts the next page is removed before that page is read, or the cursor rating is removed after it is checked, the scan continues from the stored time of that rating, including microseconds. A bulk add updates the dataset's updated time after a row is saved. The cursor sent back is that rating's stored time as text and its id. The next request uses that text whether or not the rating is still there. A cursor is rejected when the id is not a uuid, or when the time is not the stored form the server returns (`YYYY-MM-DD HH:MM:SS` with an optional fraction of up to 6 digits). A time such as `1`, or one with a `T` between the date and the clock, is rejected. So is a day the month does not have, including 29 February when the year is not a leap year. A rating that is already gone is not. The scan pages by the stored time of the last rating it read, not by a row offset. The dialog stays open while a count, a new dataset, or the add is still running. An exact 1,000 with nothing older is not reported as stopped early. A cursor id that is not a uuid is rejected. SQLite has one connection, so rating writes share one queue even when they target different datasets; other drivers keep a queue per dataset. Add to test set reads the next sequence number inside that write, after the dataset row is locked. Filling a non-empty expected answer clears the marker (D72). A Publish check still asks that row: text, JSON, and numeric evaluators score it, and a model evaluator is Error without a model call.
-   `POST /api/v1/datasets/from-questions` creates a dataset from ticked chat questions. It needs `datasets:create` and the same view key as question history. `datasets:update` is not enough. The stored question is the replay text, with the same secret redaction as the check. Each row's expected answer is empty and `needsExpectedAnswer` is set. Anyone with `datasets:view` can read those questions. A missing workspace is 401. A harness, a form, webhook, or schedule start, and an assistant are 409. A hand-picked check does not store a pass and never unblocks Publish. Only a dataset can be the passing test set. A harness, and a form, webhook, or schedule start, is 409, the same refusal as question history.
-   The publish check's `count` selects the newest distinct past questions (case and spacing ignored, newest copy kept). It is not a random sample. Omitting `count` still runs the caller's question list, capped at 10. An agentflow that starts from a form, a webhook or a schedule uses the same count on recorded execution inputs (the distinctness key is canonical JSON, so field order does not make a second input; the replay text keeps the stored field order). A form run stores `name: value` lines; the check parses those lines with `parseFormStringToJson` and does not change how executions are saved. A form string saved before the marker line is literal text, and a later message in that session keeps that stored text. The marker and escapes are only on the Start step's stored form. The model, an Agent node and `$flow.input` see the readable `name: value` lines. Webhook date, request id, trace, user agent, content length, forwarding, signature and timestamp headers do not count as a different input. Authorization, cookie, and header or query names containing token, secret, key, password or signature are returned as `[REDACTED]`. The webhook stores Authorization as that placeholder before the execution is saved, so two calls that differ only by it are one recorded input and the preview is the body alone. A kept header such as `x-bakery` still splits two deliveries that share a body. No past runs does not refuse the flow. The message names the start: submit the form, call the webhook, or wait for or trigger the schedule. Those three sentences are the same text in the dialog helper and the check service. The box for those starts is titled Check recent runs, chosen from the canvas before the check request returns. A refusal keeps that title when the canvas did not show a runs start. Progress, the stop line, an empty summary, the list name, and a failed setup use runs wording for those starts. When the canvases do not show the start, a failed setup says the check could not be loaded. When fewer runs exist than the choice, the picker is labeled Requested runs. Each recorded input includes where it came from and when it was recorded. Promote replays executions stored on the receiving server. Legacy multi-agent flows stay refused with `The check works on chatflows and agentflows.`
-   User guides say "the agent runtime". Upstream names appear only in credits, license files, the import guides and literal names (D38).
-   Guides use real screenshots taken from a running server, with made-up data.
-   Formatting follows the root Prettier config (4 spaces, single quotes, no semicolons, print width 140). Do not reformat `hermes/`.
-   The website home closing section uses the laptop mascot (`website/src/assets/cuttlely-mascot-laptop-512.webp`). The 404 page keeps the neutral pose.
-   The published npm package named `cuttlely` is `packages/cli`. The root `package.json` name is `cuttlely-workspace` and stays private. pnpm rejects two workspace projects with the same name.
-   `cuttlely check` reads `CUTTLELY_API_KEY` and calls the server in `--server` (default `http://127.0.0.1:43117`). It does not start Docker. It posts the Publish check with `count` 4. The key needs both view and update for the flow type (`chatflows:view` and `chatflows:update`, or `agentflows:view` and `agentflows:update`): update starts the check, and view is what the poll uses. A 403 exits 2 and names those permissions. After the check has started, every failure (timeout, 403, a later HTTP error, a network error, or SIGTERM or SIGINT) sends DELETE before it returns. The stop is best effort and does not change the exit code. A finished check is not stopped. The server does not start the replay if that start request is already closed (`req.aborted` or a destroyed socket), and a close before the 202 is written stops only the record that request created. `req.destroyed` is set when the body parser finishes and is not a cancel. `pnpm dev` serves the API on port 3000. `scripts/start-cuttlely.sh` and `npx cuttlely start` listen on 43117. Exit 0 when that check finishes with no Changed answers, or when `--fail-on-changed` is off. Exit 1 when `--fail-on-changed` is set and any answer is Changed. Exit 2 on timeout, a server error, a missing key, no draft, or a usage error. Exit 1 is a check result: a Changed answer in diff mode, or a failed server verdict in scored mode. `selectVerdict` returns `{ code, label }` for both. Diff mode uses `replayVerdict`. Scored mode (`--dataset` or `--gate`) reads the server `verdict` and does not rescore (D71). `--gate` reads `publishGate` from `GET /api/v1/flow-drafts/:id`. An enabled gate with a missing dataset id or an empty evaluator list exits 2 before POST, because that read withheld the ids. After a passed `--gate` verdict it reads the flow again and exits 0 only when `publishGate.enabled` is true, `block` is empty, and `result.checkId` is this check with verdict `passed`. That confirmation read waits at most 30 seconds, even when `--timeout` is longer. Otherwise it exits 2 and prints `block`, or says the saved test set changed during the check. A `--dataset` check does not read the flow again. Mixing `--gate` with `--dataset`, or a scored option with `--fail-on-changed`, exits 2. A scored 403 names the flow view and update permissions plus `datasets:view` and `evaluators:view`. Reading a stored check passes `datasets:view` and `evaluators:view` into the view: without them a dataset check returns an empty question and a null expected answer, and scores omit evaluator id and name. Recent questions and recorded form, webhook and schedule inputs stay. A model grader spreads the step's model config and sets both `model` and `modelName`, with streaming off. Token usage falls back to `estimatedTokenUsage` and generation `usage_metadata`. A provider that reports usage nowhere is bounded only by the time limit. An init failure marks only the model scores Error and keeps text, JSON and numeric scores. A per-grade abort keeps tokens already reported and does not start another model evaluator. The grader passes the check's workspace into the model node. A credential owned by another workspace is not decrypted, the grade is Error, and no model call is made. The workflows in `examples/ci/` are the commands in `docs/how-to/ci-gate.md`. `scripts/ci-examples.test.mjs` parses every file there and runs each command against a stub. The scored workflow installs `cuttlely@^1.1.0`. Scored mode is first in 1.1.0. The diff workflow leaves `npx cuttlely` unpinned.
-   The components package name is `@cuttlely/components`. New code imports that name. Saved custom functions and custom tools that require the earlier specifier keep working through the compatibility alias on the workspace root.
-   Optional node packs are directories or package names in `CUTTLELY_NODE_PACKS`. A pack's `package.json` field `cuttlely.nodePack` points at its nodes and credentials. A node name that is already loaded stays. A saved pack node keeps `nodePack` (the package name) so a canvas without that pack can name it. `packages/server/src/utils/node-pack-index.json` maps each pack node's name and label to the package name when that field is absent. `scripts/build-node-pack-index.mjs` writes it from `packages/node-pack-*/nodes`. The server build and the image build run that script with `--check` and copy the committed file into `dist` before `scripts/omit-node-packs.mjs`. They do not rewrite it. `GET /api/v1/nodes/pack-index` is the list the canvas reads. A save or an import writes `nodePack` from the index (D54). `SHIPPED_NODE_PACKS` in `packages/server/src/utils/nodePacks.ts` always loads. `CUTTLELY_NODE_PACKS` adds packs. A blank value adds nothing. The `/etc/cuttlely/no-node-packs` marker skips the shipped packs. A shipped pack is `packages/node-pack-<name>` (`@cuttlely/node-pack-<name>`). The vector store pack is the layout the next pack copies (`docs/how-to/node-packs.md`, D50). `@cuttlely/node-pack-tools-mcp` follows that layout (D51). `@cuttlely/node-pack-caches-memory` follows it too (D52). The legacy completion and chain pack follows it too (D53). Credentials another node still uses stay in `packages/components/credentials`. Dependencies only the pack imports move onto the pack. The Zep client libraries are dependencies of the packs whose nodes import them. The E2B client stays on `@cuttlely/components` because `packages/components/src/utils.ts` loads it for in-process code execution. The PostgreSQL MCP node stays in components because the analyst uses it. `@langchain/cohere` and `@langchain/baidu-qianfan` stay there because chat model and embeddings nodes still import them. `INCLUDE_NODE_PACKS=0` leaves the pack-only packages out of the image.
-   The shared server error class is `AppError` in `packages/server/src/errors/appError`. New code imports that class. The earlier module path and class name stay as a compatibility alias for one release, and both names are the same constructor. Do not set `error.name` on that class: responses and log lines already carry `Error`.
-   The server package is `@cuttlely/server`, the UI package is `@cuttlely/ui`, and the API docs package is `@cuttlely/api-docs`. Filters and docs use those names. The server CLI keeps its existing bin and adds `cuttlely-server`. The CLI config, data, and cache directories stay on the existing directory name.
-   The versioning core is `@cuttlely/versioning` (`packages/versioning`). It does not import the server. The server adapter in `packages/server/src/services/flow-versions/` implements credential storage and logging. Callers pass the saved flow in. Callers keep importing that adapter.
-   The server serves the built UI from `packages/server/dist/ui` and from `packages/ui/build`, whichever `index.html` is newer. `@cuttlely/ui` is a devDependency of the server. The UI libraries are devDependencies of the UI package. A production install does not install them. `@swc/core` and `typescript` in the components package are already devDependencies. `/`, `/index.html`, and other client routes that read `index.html` are limited to 3000 a minute per client IP. Hashed UI files and `/embed/chat.js` are not counted.
-   Workspace packages that are not published set `"private": true`: `packages/components`, `packages/server`, `packages/ui`, and `packages/api-documentation`. `packages/chat-widget` (`@cuttlely/chat`) sets `"private": false`. The root `workspaces` field is `["packages/*"]`, the same directories as `pnpm-workspace.yaml`. pnpm reads `pnpm-workspace.yaml`. npm reads the root `workspaces` field, so that field stays and matches.
-   npm publishes only from the release tag.
-   A dependency with no import in our code can still be live. `@langchain/community` loads optional peers such as `neo4j-driver` (the Neo4j node) and `epub2` (the Epub File loader), so `packages/components` must list them. Check the LangChain module a node imports before removing a package.

## Do

-   Run `pnpm install && pnpm harness:check` before and after harness changes. `node harness/check.mjs` still runs that check for one release.
-   Keep the agent runtime on `127.0.0.1`.
-   Keep model keys in in-app credentials selected on chat-model nodes (D9). When debugging, read key names, never values.
-   Build a fresh node instance per run and pass the run's real flow options to `init`. Never special-case a chat model by provider.
-   Keep partial-failure semantics: a failed specialist is reported in `agents` and Prime still answers.
-   Return a clear error when a harness has no usable model. Never invent an answer.
-   Leave a person's existing flows untouched; make a copy to demonstrate.
-   Change files under `hermes/` only through `pnpm hermes:vendor`, saving an edit as a patch (`--save-patches`). Read `hermes/` to confirm how the runtime behaves.
-   Update `.projects/cuttlely/` in the same pull request when state changes.

## Don't

-   Don't route every chat message through a harness. The Tool Agent's system message decides.
-   Don't add a chief agent loop or delegation to the scheduler path (D7).
-   Don't put a model dropdown on Prime or specialist nodes; the connected chat-model node is the control.
-   Don't turn the SSRF guard off to make a sample work (D11).
-   Don't read provider keys from the environment for harnesses, ETL embeddings or vector stores.
-   Don't store a chatflow API key in plain text or return the key columns from a list (D22).
-   Don't return a canvas from the public chatbot config of a key-protected chatflow; it keeps only the Start form fields the embed renders.
-   Don't let the analyst touch the application database (D23).
-   Don't write a live hostname, a database URL or a secret into this repository.

## Lessons

-   **An IPv4-mapped IPv6 address is reserved IPv6 on Python 3.12 even when the IPv4 inside it is public.** `blocked_address` in `packages/harness/presets/assets/cuttlely_fetch.py` judges `ipv4_mapped`, and the 6to4 and NAT64 forms it already reads, by that IPv4 address. `::ffff:8.8.8.8` is allowed. `::ffff:127.0.0.1`, `::ffff:10.0.0.1`, `::ffff:169.254.169.254`, `::ffff:100.64.0.1` and `::ffff:0.0.0.0` stay refused. The terminated 6to4 relay prefix `192.88.99.0/24` is on the explicit block list, so its mapped, compatible, 6to4 and NAT64 forms stay refused too. `3fff::/20` is on that list because Python 3.12.3 counts it as global. `192.0.0.9`, `192.0.0.10` and `2001:1::3` are globally reachable anycasts and stay refused on purpose.
-   **In the dark theme every `SvgIcon` is painted white by `packages/ui/src/themes/compStyleOverride.js`, so a color set on an icon's container does not reach the icon.** Dark Alert colors (`DARK_ALERT`) live in that file: an icon inside an Alert takes its severity color and a checkbox inside it takes the Alert text color. Dark mode is `customization.isDarkMode`; `theme.palette.mode` stays light. `PublishCheck.darkAlert.test.js` resolves the computed color (specificity, then source order, then inheritance) from the CSS that Emotion writes, because jsdom's `getComputedStyle` applies matching rules in source order without specificity and does not resolve an inherited `color`.
-   **`CUTTLELY_PUBLISH_CHECK` accepts only `true` and `false`.** `yes`, `on`, `1`, and `TRUE` are ignored on the host and refused in Server settings. The default is on, so leaving it unset does not change Publish or the check (D84).
-   **A look at another environment's versions must not use the incoming ref.** That ref is what this server offers to promote. A temporary ref, dropped after the read, keeps the offer on the previous environment.
-   **A failed try-directory delete is not a finished cleanup.** The runtime can keep `logs/errors.log` and `logs/gateway.log` open in the try directory and in each specialist directory. Close those profiles before deleting, then retry. A directory that is still there is logged once and removed on the next start, and only when it carries the try marker. A saved harness is left in place.
-   **A remembered environment-list fingerprint is not enough.** Read it back from the shared repository before treating the copy as finished. A list change that keeps the same read and copy still has to rewrite the fingerprint on the versions already copied.
-   **A missing environment-list fingerprint is not a match.** If a fingerprint record exists and this version has none, or reading that record fails, do not offer the new versions. A fingerprint publish that does not land must not be marked up to date. The only case that still offers versions with no fingerprint is the saved Dev and Prod pair, when the repository has no fingerprint record at all. A named list installs a tip only when the note on it matches.
-   **A sync pass must not re-read the environment file to pick a branch.** If the file becomes unreadable after the pass starts, substituting main publishes a Staging server onto Dev's branch and makes a reader fetch Dev. Capture the plan once, and skip the fetch and the push when the plan is invalid or the branch is missing.
-   **`pg_depend` does not record built-in objects.** A view over `pg_class` or a call to `set_config` leaves no `pg_depend` row, because objects created at initdb are pinned.
