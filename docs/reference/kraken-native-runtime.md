# Testing a saved team on Kraken

Kraken is the development branch for the 2.0 agent runtime. The standard image selects the bundled runtime by default. Use it to canary one team at a time. Keep the full image and its exact revision available for rollback.

## Checking a team before cutover

Export the saved harness canvas, then run the following command inside a built Kraken checkout or image. The command accepts a single export, a JSON array, or `-` for standard input.

```sh
node scripts/kraken-preflight.mjs ./team.canvas.json
```

Exit code 0 means the graph passed the capability check and is ready for a runtime test. Exit code 1 lists the specialists and assignments that need the bundled runtime. Exit code 2 identifies an unreadable or invalid export or an input containing no harness. Exit code 3 means the export needs an installation check for a playbook or file-enabled role. The export cannot prove which generation owns host files. A valid saved team name lets the preflight report matching local workspace files as observations. Run the saved team on the target installation and exercise the assigned file or playbook before cutover. Public Live prediction can use the published team's verified read-only playbook companions. A saved draft uses that caller's separate Try profile, including when its graph matches Live.

Run the check on the target worker image. It reads the exported assignments and probes local prerequisites for workspace files. Live credentials, host permissions, stored memory and destination-specific query stamps still need a rehearsal on the target installation.

The v1.7.15 Field Team sample has an interactive browser specialist and a Python specialist. The Upload sample grants both Python and shell execution. Preflight reports those grants even for a question that the chief could answer alone. Use the full installation for workloads that invoke interactive browsing, general Python or a shell. The on-demand policy below lets operators test eligible paths through an unchanged published team.

On demand, Field Team’s API specialist can run its saved GET card. The card keeps its public URL, tool name, description and output limit. Router mode exposes the saved tool name and its optional string query parameters. Agent mode exposes the same specialist bridge name and text input fields as v1.7.15. The unchanged Field Team sample uses `httpbin_json` in router mode and `mcp__api__requestsGet` in agent mode. Because the saved team also includes a file specialist, install the managed file worker before enabling it. Redirects must stay on the saved origin. Cards with custom headers, path templates or a custom query schema still require the full runtime.

## Enabling a canary

1. Upgrade the API and every harness worker to the same Kraken build. Keep a backup of the application database, managed files and installation encryption key.
2. Choose a saved team and set `CUTTLELY_NATIVE_PRIME_TEAMS` to its exact saved name on every process that admits turns. Separate multiple names with commas. Restart those processes.
3. Submit a known question through the chat or API your clients use. Check the answer, source documents, any attachment downloads and the run trace. Repeat with an existing chat and with a new chat. The native trace includes `engine: native`.
4. Run another turn after replacing a worker. Each queued turn carries the engine chosen when it was admitted. Jobs created by older releases use the bundled engine.

Selection applies to both router and agent mode. The default native policy, `strict`, checks the whole team before a model or tool runs. The runtime can return `native_unsupported` with the affected specialists and grants. If the bundled supervisor is unavailable and preflight cannot admit the team, the service reports runtime unavailable. A supported configuration can still fail at execution if a credential is revoked, a destination is unavailable, or a query needs to be tested against its destination again.

### Running several published chats with one key

For a private, published team, a scoped access key can issue concurrent `POST /api/v1/prediction/:id` requests for different chats. Each specialist must be able to run without a private profile on disk. Model-only specialists, Calculator and Current Date Time qualify. A specialist can also read its saved Markdown playbooks directly and search a fixed Pinecone collection with saved OpenAI embeddings. The default Pinecone namespace qualifies. A published team can combine these configurations. Each request holds the team's existing lock for its own chat. Credentials, caller permissions and the saved publication are checked as usual. Changing the publication while a request is running can fail that request before its answer is delivered.

On two physical CPU cores, a cold wave of 32 distinct signed chats using one scoped key completed 32/32 on Kraken `5245ced7`. Tagged v1.7.15 (`bb119132`) completed 1/32 and returned HTTP 409 to the other 31. The real published prediction endpoint ran the Calculator canvas in agent mode with a 450 ms simulated model. The chief answered directly. The first wave after restart reached 32 simultaneous model calls on Kraken and one on the tag. Both used the default key rate limit; immediately repeated waves can also receive HTTP 429.

Start each new conversation without a previous session token. Keep the returned `chatId` and `sessionToken` together and send both when continuing that chat. Starting a second turn in the same chat while the first is active returns HTTP 409. Wait for the first turn before retrying. Another key presenting that token receives a separate conversation. An existing signed conversation can continue after API replacement with its original owner and history.

A playbook that needs a companion file, a session or skill-directory substitution, inline processing or a host file manifest keeps the exclusive profile for that canvas and caller. A retriever with chat uploads, metadata filters or a custom embedding endpoint also keeps that profile. The same rule covers preset roles, file access, MCP, pin-first, trusted interpretation or outputs, shell, browser, code execution and other canvas tools. The same applies to draft and authoring previews, anonymous predictions, and teams using the bundled runtime. Check the actual request route when planning capacity. A direct published canvas prediction runs in the API process even when named team runs use an external worker.

### Trying a mixed team on demand

On the full installation, select the native team as above. Set `CUTTLELY_NATIVE_ROLE_POLICY=on-demand` on processes that admit new turns and restart them. The policy applies to native admissions only. A native-only installation selects every team for native execution, so this setting applies to every eligible published team there. Use `strict` or remove the setting to restore whole-team checks for new turns. Queued native turns retain their admitted policy when a worker restarts. Older queued native turns remain strict.

The on-demand policy keeps every specialist on the saved roster. A chief can answer directly or select an eligible role. Selecting a role with a saved shell or interactive browser grant fails the turn with `native_unsupported` before that role starts. The error names the specialist and its grants, including any code grant on the same role. A router plan or one agent delegation batch that selects both an eligible role and a blocked role fails before either starts. Work completed in an earlier batch keeps its actual receipts. A refused turn produces no final answer or successful chat exchange.

A specialist assigned code execution without a shell or browser can use a limited, stateless `execute_code` tool. For example, `print(sum([125, 250, 476]))` returns `851` with a successful tool receipt. The accepted form is `print(operation([integer, ...]))` with `sum`, `len`, `min`, `max`, or `sorted`. For ranked values, `print(sorted([3, -5, 3], reverse=True)[:2])` returns `[3, 3]`. Ascending and descending order preserve duplicate values. A prefix limit from 0 through 128 selects that many entries. Each call accepts up to 128 signed decimal integers, 64 digits per integer, and 8,192 source characters. An empty `min` or `max` produces the corresponding tool error. A request outside that scope fails the turn. General Python, persistent kernels, arbitrary file access and network calls still require the bundled runtime.

Authorization, canvas ownership, file bindings, MCP grants and credential checks still apply. Only a saved team or its verified published canvas qualifies. Unpublished Try runs retain strict admission. If a published team changes after an on-demand job enters the queue, submit a new authorized turn against the updated version. The export preflight always reports the full saved grants, including general code, shell and browser.

For a canary, exercise a chief-only request, a request invoking a known supported tool, and one selecting each blocked specialist. Check the real tool receipt for the supported request, the error and failed run status for the blocked requests, and the result of the same calls through any saved calling chatflow. Repeat after replacing a worker. Keep the bundled runtime available for workflows that need the deferred capabilities.

### Render a reviewed static page with a saved browser specialist

An operator can enable a limited page read for an existing specialist whose only work capability is Browser. The published team must use native **on-demand** role selection. On a stripped host, this route stays unavailable until the matching Playwright Chromium build and its system libraries are installed. The browser must be able to start with its sandbox enabled. Set `PLAYWRIGHT_BROWSERS_PATH` before starting each serving process if the browser installation uses a shared location. Strict compatibility inventory continues to list the complete Browser capability as unsupported.

Create an explicit grant in `CUTTLELY_NATIVE_STATIC_PAGES` on the API and each worker that will serve the team. Obtain the workspace ID, canvas ID and server-issued generation from the saved team record. The generation is its `createdAt` value. A replacement team needs a new grant. For example:

```json
[
    {
        "workspaceId": "<workspace ID>",
        "flowId": "<published canvas ID>",
        "generation": "<saved team createdAt>",
        "role": "<saved specialist name>",
        "url": "https://catalog.example.org/shipping",
        "redirects": ["https://catalog.example.org/shipping-hours"]
    }
]
```

The caller must include one unambiguous, reviewed public HTTP(S) URL in the original message. A repeated copy of that URL is allowed. The endpoint must use a standard port and a URL without credentials, query parameters or a fragment. The reader validates and pins a public address at each request and accepts at most three explicitly listed same-origin redirects. This applies to direct authenticated published predictions and named runs for the same saved generation and authorized caller. Nested flow arguments can be generated by a model, so that entry point cannot authorize a page. The model can request `browser_navigate` for the approved page and `browser_snapshot(full=true)` for the current delegation. Navigation returns the title, and the full snapshot returns the text and accessible structure. Compact snapshots and interaction references require the bundled runtime. Source pages and model-suggested links cannot authorize another destination.

The reader accepts up to 64 KiB of simple static HTML, up to 1,500 elements and 32 levels of nesting. It renders headings, paragraphs, lists, tables and basic semantic containers. Attributes, scripts, styles, forms, media, frames and interactive elements require a different capability. Chromium renders a local copy with JavaScript and network access disabled in a fresh profile. It receives no site credentials or stored cookies. A full snapshot can contain up to 20,000 characters. For plain source text and citations, the Web Browser card’s **Return source text** setting uses the HTTP reader and requires no Chromium installation.

Budget for the renderer independently of model and database memory. Each serving process can launch two concurrent Chromium instances. A third simultaneous render receives HTTP 409. In a local two-chat rehearsal, two browsers with 20 operating-system processes together showed about 1.7 GiB of summed RSS. This figure counts shared pages once per process and excludes the application and database. Measure the memory limit on the intended host with representative documents; a 512 MiB service has no qualification from this rehearsal. Each read has a 10-second deadline. Streaming disconnect cancels the read and closes its browser. An accepted non-streaming prediction can finish after the client disconnects. Editing the published role during a read prevents further approved fetches and answer delivery. Operators can run `bash scripts/kraken-static-page-check.sh` on a disposable Linux test host with the browser, the Field Team file dependencies, iproute2 and util-linux installed. The fixture binds its synthetic catalog in a new network namespace and checks the signed named, agent and router entry points.

A saved **Retriever Tool** named `catalog` on a specialist named `research` is offered as `mcp__research__catalog` in agent mode. Router mode uses the same qualified name when the specialist runs through the agent bridge. The inline router offers `catalog` with the card’s own input schema. A bridge call accepts a lookup string in `input` or `query`. An existing native instruction can still call the short name when it identifies one assigned retriever unambiguously.

On a bridge-backed role, use the distinct names in the model’s tool list when two cards share a name. Each resolves to its own card, saved credential, namespace and result limit. A foreign role’s name or an ambiguous short name fails before retrieval. If two names normalize to the same qualified identifier, give the cards distinct names before cutover.

### Testing a team that searches local documents

The Chief of Staff example builds an in-memory index from its saved Plain Text note using Local Hash Embeddings. On a replacement worker the saved canvas supplies the note, source metadata and embedding settings. Ask which embeddings built the vectors. Router mode returns the retrieved document in `sources`. Agent mode passes the note to the researcher as a tool result and returns the answer with an empty outer `sources` list, matching the released team.

The Research example uses a Custom Retriever with text output. Ask when the example archive opens and check for **09:00 UTC** and **Research Handbook** in the answer. The saved format places the citation in the text. An older Research canvas can have an empty **Vector Store** input. Connect the operator's intended store on that canvas before cutover. The updated first-party example contains its own note.

AI Builder also includes the Research example. Its plan preserves the selected output and document metadata when it rebuilds the canvas. After saving a generated team, run the sample question through its prediction endpoint to check the answer and citation.

Other local Custom Retriever cards can select **Document** or **Retriever** output. With Document selected, the researcher gets the formatted note. With Retriever selected, it gets the raw matching note. Router mode includes structured sources for both selections. Agent mode returns the answer without an outer source list. The prediction fixture exercises both selections after a PostgreSQL host loses its application disk. [Public prediction fixture](../../scripts/kraken-local-research-prediction.test.mjs)

For a new template imported through the API, supply a valid harness name and select a saved credential on its chat model. For a published team, exercise its existing binding. A PostgreSQL Analyst card with no selected actions or saved pins grants no queries. With the isolated Analyst disabled and no supplied destination, a direct attempt to invoke that card reports its missing configuration. A team that needs SQL must have an eligible configured Analyst action.

### Playbook references on replacement workers

The normal `skill_view` call expands `${HERMES_SESSION_ID}` for the current specialist turn and `${HERMES_SKILL_DIR}` to `/skills/harness-playbooks/<book>`. Reading `SKILL.md` by its explicit file path returns the original Markdown. A saved canvas carries the playbook body. For an operator-provided companion, put the same immutable file on each worker and include its digest and assignment in the host manifest selected by `CUTTLELY_HOST_FILE_MANIFEST`.

```json
[
    {
        "path": "runtime/profiles/demo--reader/skills/harness-playbooks/handbook/references/guide.md",
        "sha256": "<64 lowercase hexadecimal digits>",
        "playbook": {
            "workspaceId": "<saved workspace id>",
            "chatflowId": "<saved harness canvas id>",
            "generation": "<createdAt from the saved harness record>"
        }
    }
]
```

The example assigns `references/guide.md` to the `handbook` playbook of specialist `reader` on team `demo`. An owned draft also needs its exact `tryId` and draft profile path. Older manifest rows containing only a path and digest need a separate matching digest for the compiled parent harness-roster.json, with the same canvas generation and saved assignment. Rehearse on a replacement worker with the same manifest and files. Preflight reports unresolved dependencies. Inline shell execution in a playbook requires the bundled runtime. If the saved team changes during a run that uses a playbook, the worker checks the revision again before sending more answer text or attachments. A client can retry on the new revision.

### Workspace MCP status endpoint

A saved Custom MCP Server Tool can use Streamable HTTP or SSE for the read-only `ops_status` action. Register its exact workspace, saved server ID, URL and action on the API and the workers using `CUTTLELY_NATIVE_MCP_ENDPOINTS`. An example configuration follows.

```json
[{ "workspaceId": "<workspace>", "serverId": "<saved-server-uuid>", "url": "https://ops.example.org/mcp", "actions": ["ops_status"] }]
```

For SSE, add `ssePostUrl` with the exact same-origin message endpoint. Keep the Authorization or X-API-Key header in the existing encrypted server credential. The runtime checks the server record, grant and tool schema before dispatch. A missing grant, revoked credential or changed schema stops the action. An offline export needs its saved workspace ID to match this grant during preflight.

### Specialist workspace files

On a supported Linux host, a file-enabled specialist can read, write, search and patch its own workspace and return files saved under `output/` to the chat. Use a signed-in account or an identified API key. Upload a representative file through the chat, ask the specialist to transform it, download the result and check the bytes. Repeat under the original identity after replacing a worker. Other users and keys may choose the same chat ID and retain separate workspaces.

Each workspace is limited to 256 files and 64 MiB of decoded content. It uses the selected harness session store. PostgreSQL preserves these workspaces across empty-disk replacements. SQLite requires a retained data volume. The image ships a fixed document decoder and search binary. The worker requires Linux Landlock ABI 3 or later and libseccomp. On a host that cannot enforce the file boundary, preflight identifies the team as requiring the bundled engine. A configured hosted OCR service or language server is a separate dependency. Preflight reports these settings so the operator can retain the full runtime for teams that use them. Rehearse with the documents the team processes, including scanned PDFs.

When a published file-enabled team runs, native admission checks the specialist’s shared legacy workspace and the Try workspace for the signed-in user or API key making the request. Files in the shared workspace block native use of that specialist’s team for every caller. Files in a caller’s Try workspace block that caller. Other callers can continue when their own checks pass. Cuttlely leaves the original files in place.

On a full installation with a healthy bundled runtime, a native canary blocked by these files names the specialist and reports `existing workspace files need owner-scoped upload`. On a native-only installation, or when the bundled runtime is unavailable, availability preflight returns HTTP 503 (`RUNTIME_UNAVAILABLE`) for the same blocked prediction. Neither response exposes filenames, file contents or host paths. If a caller reports a 503, the operator should check runtime readiness first. If the deployment is healthy, check the team’s shared workspace and that caller’s Try workspace with the owner before retrying. The export preflight can identify a matching shared workspace. To locate a caller’s private workspace in a backup, match the saved flow and caller IDs to the `harness-try-flow` and `harness-try-owner` markers. If the backup is incomplete, confirm ownership before assigning files to a chat.

Before switching engines, back up the affected workspace and verify that the backup opens. Have each owner identify which files belong in each chat. Archive the original files outside the live legacy workspace, then retry native prediction and re-upload only the needed copies through the intended chat using that owner’s account or scoped key. Keep the backup until each owner has opened the uploaded files and checked the required outputs.

### Sampling a CSV or TSV upload

The saved Upload team’s Python specialist can sample a verified CSV or TSV up to 4 MiB in on-demand mode. Attach the file to the current prediction and ask for a sample. The specialist uses the packaged sampler to return the row count, headers, first and last five rows and, when the columns are present, amount totals and means for the five leading regions. Output is capped at 4,000 characters. Each caller sees only the upload admitted for that chat. Resend the attachment if its stored bytes change before the worker reads it.

### Sampling an Excel workbook

Attach an XLSX workbook of up to 4 MiB and ask the Upload specialist to sample a named sheet or the first visible sheet. It returns visible sheet names, headers, the row count and previews of the first and last five data rows. A numeric `amount` column produces a sum. The preview shortens wide or long values to keep the report within 4,000 characters. The selected worksheet can have up to 5,000 rows and 64 columns. The reader refuses external relationships, macros and formula cells on the selected sheet. Export a values-only copy if the workbook relies on those features. Workers need the native report assets for the XLSX reader. [Native report setup](#reporting-on-an-uploaded-csv)

### Reporting on an uploaded CSV

A direct request to repeat a short caller-supplied literal can complete without invoking an Analyst. A conditional answer, request for data, or request for a verified report still needs source evidence.

An authenticated chat or API client can attach a CSV and ask for a table or bar chart. Use a specialist with File Access and an eligible PostgreSQL Analyst query grant. An on-demand code specialist with File Access can also process the verified upload directly. The CSV operation uses the uploaded bytes and requires no database grant for that path. The report tool reads the verified original upload, including small CSVs that the chat displays inline. Each worker must be able to reopen the original stored bytes. PostgreSQL and hybrid installations use their configured file store. A changed file fails verification and the caller can send it again.

For example, ask “From the attached CSV, group by Region, sum Net, and return the table and a bar chart.” The response identifies the source, counted rows and groups, and includes a downloadable CSV and optional PNG. Supported operations are count, sum, mean, minimum and maximum. Means round to eight decimal places. The calculation supports 4 MiB, 50,000 rows and 250 groups, with up to 40 groups in a chart. A database request still needs its own database result. Protected saved-query outputs keep their existing verification rules.

For a PDF, Word document or Excel workbook, ask for the format by name. The report tool accepts `documentFormats` with one or more of `pdf`, `docx` and `xlsx`. Each document uses the same verified rows and totals as the CSV. Excel preserves high-precision decimal values as text. Each specialist can return up to four report files per turn, including the CSV, plus its chart. If the fixed PDF font cannot display a label, request the Word or Excel version.

The Docker image includes the Linux document renderer. For a source installation, install its pinned dependencies with `/usr/bin/python3 scripts/install-native-report-assets.py /opt/cuttlely-report-assets` and provide the DejaVu Sans regular and bold fonts. If the operator selects another dependency directory, set `CUTTLELY_NATIVE_REPORT_ASSETS` to the same absolute path on each worker. Rehearse an actual download after replacement.

### Primary and fallback model responses

When a provider returns several tool calls in one reply, the runtime pairs each result with its original request and preserves their order. A reused or omitted pairing ID receives a stable replacement before dispatch.

A specialist with a single model streams text as it arrives. When a primary and fallback can compete, the native runtime waits for a winner before sending that specialist’s text. A slow primary or backup may already have generated a different draft. The client receives the selected answer once. Inspect the run trace to see which model answered and its token usage. If the provider omits usage, the count is unknown. A reported zero for cached prompt tokens is retained.

For custom streaming clients, `harness.final` contains the complete answer. Replace the displayed answer with that text and ignore any later answer deltas for the same turn. In agent mode, both v1.7.15 and Kraken can flush a buffered `harness.partial` after the final event. A one-word answer can arrive entirely in that last delta. Both engines send `harness.recorded` when conversation metadata is available.

On the streaming prediction endpoint, a native Analyst with verified output delivers its attachments before the protected answer. If the source check fails or the verified attachments cannot be delivered, the stream reports an error and withholds the protected answer. On `POST /api/v1/harnesses/:name/runs`, successful streaming clients receive the verified answer events followed by `artifacts`. The server checks that every required attachment is available before sending those events. A failed delivery returns a stream error or an HTTP error for JSON callers.

### Conversation search

Signed-in users and identified API keys can use `session_search` on a saved agent-mode team for user/assistant exchanges whose ownership the installation recorded. Test with an existing chat, switch engines, then ask for a specific earlier answer. Verify a second caller and a different chat cannot retrieve it. A successful v1.7.15 queued turn can establish ownership when its saved caller, workspace, canvas generation and chat agree. To find an earlier question followed by a long report, pass `role_filter: "user"` with the search query. Only messages in the requested roles count toward the per-message search limit. A matching turn can include a bounded preview of the report. The turn-count limit still applies. An old bundled transcript can also exist without that association. Keep the bundled installation available for older transcripts or profile-wide memory awaiting operator review. The application’s ordinary stored chat messages, the search index and the bundled runtime’s private transcript have different recovery and access rules.

### If a worker stops during a tool call

Each external worker runs one queued job at a time. With PostgreSQL side stores, budget one additional database connection per worker for `LISTEN`. A notification carries no payload and wakes an idle worker to check the queue. If the database or connection pooler does not support notifications, denies them, or drops the connection, the worker continues polling. The database claim still decides which worker can run a job. A second turn for the same session receives HTTP 409 while the first turn holds it.

Workers check the saved team again during a run so a change to its permissions takes effect. With the usual PostgreSQL table grants, concurrent readers share a lock on the saved-team table. A pending edit can briefly delay lookups for other teams. An execution role with column-level update permission can lock an individual row. A role with read-only access, or a row policy allowing the role to read a team it cannot lock, can load that team under its existing PostgreSQL permissions. All three paths wait for a publication or revocation made through Cuttlely. For direct SQL edits, a read-only role sees the last committed version until the edit commits. PostgreSQL continues to enforce its SELECT privileges and row policies at each lookup.

Queued native calls record their selection, dispatch and acknowledgement in the application queue. If a worker disappears before acknowledgement, the job reports an uncertain outcome and retains the call ID for investigation. Check the destination before retrying an external action. A call still queued has not reached its tool. A confirmed call has already returned to the worker. The public event stream keeps its existing event types. Call arguments and tool results are excluded from these receipts.

For an asynchronous submission, keep its run ID. After an API restart, poll `GET /api/v1/harnesses/:name/runs/:runId/result` with the original caller. A worker that retained its lease can finish and save the answer for the replacement API. If the worker died, polling after its lease expires reports `worker_lost` and identifies an unconfirmed action. An operator who stops jobs for a storage upgrade can also see an unconfirmed action on a cancelled run.

An admitted PostgreSQL background run records its answer and usage in the same transaction. If the worker returned an answer while a usage write was failing, the caller can receive HTTP 503 while polling. Restore the database write path and poll the same run ID. The API can then deliver the saved answer and credit its workspace once. Submitting the question again starts a new run.

The history keeps 100 settled runs per team. Active runs and accepted results awaiting accounting survive that limit. A healthy inline or external worker revisits pending PostgreSQL completions after the database recovers. It can publish the original result and record usage even if the caller has gone away.

When a caller waits for a queued PostgreSQL run, each poll reads its public events and job status together. If completion and the wait deadline coincide, the queue checks which operation committed first. A completed job returns its saved result and final events. An active job receives a cancellation request and the caller receives `worker_timeout`.

The PostgreSQL queue groups pending stream reads on a shared polling timer within each API process. Each waiting request reads from its own job and event cursor. Independent chats can acquire or release their turn leases concurrently. Admission and expired-lease recovery still serialize conflicting turns. Cancellation checks read committed state, and a tool call still requires its durable dispatch receipt. These changes require no new worker or database setting.

Workers check cancellation every 25 ms during an active turn. While waiting on a provider, each worker renews the job timestamp about twice a second. A disconnect is recorded on the job so another worker can stop it. If the database loses the acknowledgement, the waiter checks the saved flag before retrying.

The native MCP cooldown applies to one conversation owner, team generation, specialist and tool server in the process serving the call. Three consecutive failures pause that scope for 60 seconds. Another owner can use the same chat ID and tool server independently. A turn without a verified conversation owner has its own cooldown scope.

On PostgreSQL, loss of the storage coordinator makes both `/api/v1/ping` and `/api/v1/ping/live` return HTTP 503. The operator can inspect storage status even if an ordinary database query still succeeds. Restore database connectivity and replace the affected process. A standalone worker exits with status 1 on coordinator loss. Configure its service supervisor to restart it on failure. A normal SIGTERM shutdown exits with status 0.

A successful preflight establishes that the runtime recognizes the saved configuration. Exercise the actual question and tools. A direct Prime answer alone does not test specialist execution.

## Previewing an installation without the bundled runtime

Run the named-team canary and the team’s real workflow first. A native-only image selects the native engine for every team. For example, a named team with an interactive browser role receives HTTP 503 (`RUNTIME_UNAVAILABLE`) before a model or tool runs in a native-only image. The same request on a healthy full installation that selects the team for native execution returns HTTP 422 and identifies the browser requirement. Run preflight on the saved team to find which role needs the bundled runtime. A team admitted on demand can still fail later when it selects a blocked specialist or requests an unsupported action. On the standard image, keep that team on the bundled engine.

Build the preview locally with the same source revision on the API and workers.

```sh
docker build --build-arg INCLUDE_BUNDLED_RUNTIME=0 -t cuttlely-native .
```

Use the normal image entrypoint. The application starts the native runtime directly. An external worker starts with `node packages/harness/worker.mjs`. Set `CUTTLELY_HARNESS_QUEUE=external` and `CUTTLELY_HARNESS_WORKERS=0` on the API when deploying workers as separate services. Keep the API and worker on the same application database and installation key. Confirm strict readiness at `/api/v1/ping`, submit a real team run, and check the worker’s resulting answer and tool trace. A fresh data directory is sufficient after a verified PostgreSQL storage cutover. SQLite needs a retained volume. Hybrid uses the same durable PostgreSQL stores and the configured private object bucket for managed files. Operator-provided local dependencies still need to be available on each replacement host.

The native image can be built from a checkout that omits the entire bundled runtime source directory. It ships the Cuttlely-authored recovery helper from the ETL package. The full-checkout compatibility gate checks that this file matches its copy in the bundled runtime byte for byte. The image uses that recovery code for encrypted runtime settings and SQLite session images stored in PostgreSQL. An incorrect installation key stops recovery. To roll back, drain native jobs and redeploy the full image on the API and every worker with the same database and key. Clear any named canary selection before admitting bundled jobs. A binary rollback and a storage rollback are separate operations.

Run `bash scripts/check-kraken-package.sh` from a full, built checkout to create the isolated source export and exercise the complete package gate. The gate needs the pinned Node and pnpm, disposable PostgreSQL and a standalone Python with sqlite3 serialization, pg8000 and cryptography. Set `CUTTLELY_RECOVERY_PYTHON` to that interpreter when it differs from `python3`. The script removes its temporary install on exit.

To verify an existing local native build, set `CUTTLELY_TEST_NATIVE_PACKAGE` to the absolute path of the separate installed native package and run the following command in a built full checkout with the bundled runtime available. The tests start their own API and worker, use disposable PostgreSQL databases and simulate the model.

```sh
node --test scripts/kraken-ops.test.mjs scripts/kraken-upgrade.test.mjs
```

The package gate covers a fresh install and replacement of an existing installation with separate empty API and worker disks. It checks the saved caller, team, credential, schedule and chat, exercises the Ops MCP tool and restores encrypted settings and a real bundled SQLite transcript. It also checks rejection of an incorrect key and recovery after redeploying the full package.

## Rollback

Remove the team name from `CUTTLELY_NATIVE_PRIME_TEAMS` and restart the admitting processes. New turns use the bundled runtime. Let previously admitted turns drain on their recorded engine before removing their workers. Continue the same chat and check that the prior response and any stored attachments are available. Engine selection does not change the application's storage mode.

On a PostgreSQL installation, rehearse a question that requires the bundled chief to delegate. Check that the run records the intended specialist as completed and that the answer contains the expected tool result. A direct answer from the chief cannot establish this. For the published read-only Ops example, keep the operator’s existing grants for the saved command and script on every worker.

The full Kraken build can record bundled specialist progress in PostgreSQL for published agent-mode teams that use directly assigned chat models with basic generation options and model-only specialists or the packaged read-only Ops action. The progress record belongs to the live chat turn and saved team revision. Drafts, custom modules, other MCP actions, preset roles, playbooks and file-enabled roles need their own rollback rehearsal. Keep the previous working deployment and its storage available until that rehearsal succeeds.

If you switch this team back to native, use the same account or access key and chat to search for a specific answer from the bundled turn. This checks the stored ownership record in addition to the visible chat history. Open an earlier attachment from the saved conversation to verify its download as well.

Provider calls in these compatibility fixtures are simulated.

### Concurrency acceptance for a release

The release goal is to serve at least as many simultaneous authenticated chat connections as the v1.7.15 bundled runtime at equal or better end-to-end p95 latency and verified throughput. Evaluate each route and workload separately. For streaming clients, count distinct connections held open at the same time and confirm each stream delivers its own result. In the per-round report, `peakRequestsOnWire` counts overlapping sent requests awaiting completion. `peakOpenSseResponses` counts overlapping streams from receipt of their response headers through end of stream.

Compare the candidate with tagged v1.7.15 (`bb1191321688de52a405dfb88ab43826250c814f`) through the same authenticated streaming endpoint. The direct team comparison uses `POST /api/v1/harnesses/:name/runs` with streaming enabled. Measure the saved chatflow’s `/prediction` path separately when that is the client entry point. Use the same saved graph, simulated provider settings, caller permissions, PostgreSQL snapshot, worker concurrency, hardware limits and client. Run each implementation against its own fresh restore. Pair a cold wave on newly started processes with a warm wave that reuses the running services and chats. Give each turn a distinct input and expected answer.

In the full PostgreSQL test, the stock v1.7.15 Ops sample returned no verified status across 18 fresh and warm requests at one and eight concurrent callers. A separate control on Kraken `5245ced7` and the same release tag used the same newline-compatible Ops MCP server on both engines, with PostgreSQL for the application database and local storage for side stores. Its timings measure successful calls in that configuration.

In a matched hosted run on Kraken `e6c38d20` and v1.7.15, each API shared one CPU core and 2 GiB of memory with two external workers. At 32 concurrent authenticated connections, all 512 Calculator turns across eight deployments produced the expected answer and saved run. Fresh-chat p95 was 23.82 seconds on Kraken and 31.41 seconds on v1.7.15, with 1.35 and 1.00 verified turns per second respectively. Continuing-chat p95 was 24.13 and 30.29 seconds, with 1.32 and 1.05 verified turns per second. Both engines used the same HTTPS client, private PostgreSQL 16 and a fixed Calculator shortcut that made zero model calls. In the separate five-configuration local comparison, Kraken met both targets in nine of ten fresh or continuing chat comparisons. The single fresh-chat cohort missed both.

A subsequent local run on Kraken `53dcf188` verified all 1,616 Calculator turns across both engines. At one, eight and 32 concurrent clients with one worker, and 32 clients with two and four workers, Kraken met both performance targets for fresh and continuing chats in all ten comparisons. With 32 clients and four workers, fresh-chat p95 was 2.08 seconds on Kraken and 2.84 seconds on v1.7.15. Verified throughput was 15.00 and 11.09 turns per second. Continuing-chat p95 was 3.13 and 3.15 seconds and verified throughput was 11.82 and 10.24 turns per second. These local runs used the same Calculator shortcut and made zero model calls.

The comparison verifies the client version, execution engine, number of connections, completed chats and matching run receipts. It reports cold and warm results separately. A missing receipt, incomplete wave, slower pooled p95 or lower verified throughput makes the command exit unsuccessfully. The client measures concurrent connections at ingress. For release sign-off, pass all five configuration manifests to `node scripts/kraken-calculator-parity.mjs --matrix <1x1.json> <8x1.json> <32x1.json> <32x2.json> <32x4.json>`. The first number is the client count and the second is the external worker count. Supply the same candidate revision and load client for every configuration. The command retains each configuration’s cold and warm results and exits unsuccessfully if any configuration is missing, duplicated or below either threshold.

1. Compare 1, 8 and 32 concurrent requests at a fixed worker count. At a load of 32, repeat with fleets of 1, 2 and 4 external workers. Record peak open connections, overlapping model calls and verified tool calls separately. For queued runs, record queue wait, active jobs and completed jobs per worker. Each external worker executes one queued job at a time. Scale external execution with the worker process count. For an inline queue, hold `CUTTLELY_HARNESS_WORKER_CONCURRENCY` fixed across engines. It defaults to four active jobs in the server. Public `/prediction` runs directly in the API process. Include a lightweight API ping during each wave.
2. Alternate release and candidate order. Run at least two balanced repetitions per configuration. Use four when variation is large enough to change a close decision. Pool the per-turn samples within each matched load, worker count and temperature. Report each repetition so the spread remains visible.
3. Report admission latency, end-to-end p50 and p95, successful completions per second, and API ping latency and failures. List request errors, timeouts and cancellations. At each matched load, the candidate must equal or exceed the tag’s fraction of requests with a correct result and its verified completions per second, with end-to-end p95 no higher. Report the highest tested simultaneous connection count that met all criteria for each worker configuration.
4. Require every successful answer to match its own input, caller, chat and saved run. For a tool workload, verify the expected specialist actually invoked its tool and the final answer contains the result for that request. Reconcile submitted requests with terminal jobs, confirmed tool calls and delivered events. The Calculator client records request start, response headers, first answer and EOF on the same client clock. First answer is the arrival of the complete SSE frame containing the first nonblank answer-phase partial or the verified final answer, whichever appears first. The report includes the count of each event type and request-to-first-answer p50/p95 for cohorts with complete observations. Frames received in one chunk share a timestamp. Older captures can report headers and EOF only. The capacity thresholds continue to use end-to-end p95 and verified completions per second.

Sample per-process RSS at the same instants and report the peak observed fleet sum. RSS counts shared pages in each process; use proportional set size (PSS) or a dedicated cgroup memory peak when reporting those measures. List database, provider and client resources separately. Capture idle, startup and active memory for the same process boundaries on each engine.

For model-assisted runs, reconcile each verified turn's model calls with provider-reported input, output and cached tokens, including retries. Report measured calls and usage-covered calls. Preserve missing token fields as unavailable. A confirmed zero-call Calculator fast path has no model usage for that workload. For a cost estimate record the model, dated rates, currency and cache billing rules. Simulated usage remains a fixture measure.

Repeat a representative run with an existing long conversation. Compare the recent messages, summary and pins with their original values. Verify that the stored transcript is intact and another caller cannot retrieve the conversation through session recall. Record the original transcript length and the end-to-end timing separately from fresh chats.

Record the exact revisions, fixture and measured configurations. A result for one workload, temperature or worker count establishes performance only for those conditions. Acceptance also requires the functional and recovery checks above.
