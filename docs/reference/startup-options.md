# Startup options

Every option the [Server settings API](./server-settings-api.md) exposes, in one list. The list is the settings registry plus the fixed host-only list. `GET /api/v1/server-settings` returns the registry in `settings`. `GET /api/v1/server-settings/read-only` returns the host-only list in `settings`. Both responses are the whole list. They do not take `cursor` or `limit`, and they do not page.

A secret setting and every host-only key are named here and marked **not shown**. The table does not include the value, a default that would be the value, a length, a hash, a token, a key, or a connection string. The API follows the same rule: a secret is omitted from the response, and a host-only row is `key`, `set`, `source`, and `readOnly`.

**Where it can be set** is the host and then Server settings, except time limits marked `limit`, `CUTTLELY_HISTORY_KEEP`, and invite and mail settings, where a saved value wins over the host. Fixed display fields read no environment variable and cannot be saved. `SMTP_PASSWORD` and the other host-only keys can be set only on the host. **Restart** is No for live limits, runtime settings that apply on the next use, and fixed display fields. Restart limits say “Restart to apply.” in their help and appear in the pending restart banner; saving never stops running work. Every other option applies at the next start.

Access-key enforcement is `INBOUND_ACCESS_V2` (`off`, `shadow`, `on`; default `off`). The instance-operator Server settings control applies on the next request and persists across restarts. A host value wins and locks it, including forced `off` for recovery. Invalid saved values resolve to `off`; invalid nonempty host values retain 503. [Rollout and compatibility warnings](./access-keys.md#rollout-and-migration).

The valid private operator binding is the default when `CUTTLELY_INSTANCE_OPERATOR` is entirely unset. Only actual host CLI bindings grandfather automatically. Legacy installs explicitly claim in Server settings using host-log proof; routine transfer/revoke and fresh-proof rebind are in the panel. The CLI is emergency recovery only. Host JSON/`none`/empty/invalid precedence remains immutable from the panel. Operator authority and proof state are outside generic settings. See [operator onboarding and recovery](../how-to/instance-operator.md).

The publish check switch is `CUTTLELY_PUBLISH_CHECK`. The default is `true`. Accepted values are exactly `true` and `false`. How a host value wins, and the error codes, are in the [Server settings API](./server-settings-api.md#publish-check-switch).

The localhost switch for HTTP building blocks is `HTTP_ALLOW_LOCALHOST`. The default is `false`. Accepted values are exactly `true` and `false`. When it is `true`, any flow author can reach any service listening on the server’s own localhost (`127.0.0.0/8` and `::1`, and the names `localhost` and `ip6-localhost`) from HTTP building blocks. Nothing else is opened: `0.0.0.0`, `::`, link-local and cloud metadata addresses, private ranges, and every `HTTP_DENY_LIST` entry stay blocked. It applies on the next request, without a restart. When `HTTP_SECURITY_CHECK` is `false`, the built-in block list is off, so loopback is already reachable and this switch changes nothing; only `HTTP_DENY_LIST` entries are blocked.

The agent runtime concurrency limit is `CUTTLELY_HERMES_MAX_CONCURRENT_RUNS`. The default is `10`. Accepted values are whole numbers from `1` to `50`, or `0` for no limit; negative values and values above `50` are refused. Higher values use more memory and CPU. It applies after a restart: the start script writes it to `gateway.api_server.max_concurrent_runs` in the agent runtime’s `config.yaml` and keeps the other keys there.

For [long-running queries and tasks](../how-to/server-settings.md#long-running-queries-and-tasks), set the env vars today; admin Server Settings fields for these limits are coming in the same release. `CUTTLELY_ANALYST_STATEMENT_TIMEOUT_MS` defaults to 15000 ms and accepts up to 3600000 ms (1 hour); positive values below 1000 become 1000, and invalid or higher values fall back to 15000 with a warning once. `CUTTLELY_HARNESS_TOOL_TIMEOUT_MS` accepts integer milliseconds from 1 to 3660000 inclusive, rounded up to seconds for MCP. Unset, blank, invalid or out-of-range values keep the 300 s MCP default, the 420 s Hermes per-tool default and the 130 s stdio bridge wait. When set, the bridge wait and Hermes `timeouts.tools.sequential_call` and `timeouts.tools.concurrent_batch` use the rounded tool timeout plus 60 s. This setting covers MCP tools; shell stays capped at 600 s and code execution at 300 s, so use a pipeline job for those longer tasks. A long-running remote HTTP MCP tool must use streamable HTTP (SSE) and send progress at least every 300 s; a server that replies with a single JSON response can't, so run that work as a pipeline job. The built-in Analyst and database tools run through the local bridge, not HTTP, so they're limited only by the tool and query settings. `CUTTLELY_HERMES_HEALTH_TIMEOUT` sets the agent-runtime health probe wait in seconds: default 2, range 1–30, with invalid or out-of-range values using 2 and logging a warning.

Pinned queries are `CUTTLELY_PINNED_QUERIES`. They are on only when the value is exactly `1` or `true`. Any other value, including `false`, `yes`, `on`, `TRUE`, and an empty value, leaves them off. Off removes the pinned query tools at the next start.

The trace content limit is `CUTTLELY_OTEL_TRACES_CONTENT_MAX`, the characters each `content.input` and `content.output` span attribute keeps. The default is `4000`. Accepted values are a positive whole number, or `0` for no limit. No limit sends the full question and answer text to your OpenTelemetry collector, so use it only with a collector you trust. [Run traces](../how-to/observability.md#full-question-and-answer-text).

## Inbound access-key rollout (host only)

`INBOUND_ACCESS_V2` defaults to `off`. Only `off`, `shadow` and `on` are accepted; another nonempty value returns `503` when checked. Set it on the host and restart. `off` retains legacy authorization; new issuance, policy editing and rotation require `on`, while revocation remains available. `shadow` serves legacy decisions and compares scoped flow authorization without charging quotas. It does not simulate every route or limit. Validate a restored-backup migration with `node scripts/access-keys-migration-report.cjs` and review shadow mismatches before enabling `on`. Existing keys keep working without rotation. [Access keys](./access-keys.md#rollout-and-migration).

`CUTTLELY_API_KEY_INSTANCES` defaults to `1`. Any value whose numeric conversion is not `1` refuses access-key admission with `503`; it does not configure a shared limiter. Minute counters are per process and reset on restart. Daily/monthly UTC counters persist in SQL; Redis/multi-instance limiting is not implemented. These flags are host-only and their values are not exposed through Server settings.

## First owner from host configuration (host only)

`CUTTLELY_INITIAL_OWNER_EMAIL` with exactly one of `CUTTLELY_INITIAL_OWNER_PASSWORD_HASH_FILE`, `CUTTLELY_INITIAL_OWNER_PASSWORD_FILE`, `CUTTLELY_INITIAL_OWNER_PASSWORD_HASH` or `CUTTLELY_INITIAL_OWNER_PASSWORD` creates the first owner when the server starts on an empty database, before it listens, so no setup code is printed. `CUTTLELY_INITIAL_OWNER_NAME` is optional. It needs `CUTTLELY_LOCAL_ADMIN=true` and no AuthKit. Once any account exists the variables are ignored with a warning, and nothing is changed. On an empty database an invalid value stops the start with exit code 1 instead of offering the setup link. These variables are not settings: Server settings neither shows nor changes them. [Create the first owner from host configuration](../how-to/sign-in.md#from-host-configuration).
