# Disk storage inventory for the PostgreSQL upgrade

PostgreSQL hosts can move application-owned SQLite side stores from Server Settings. [Operator upgrade and rollback guide](../how-to/postgres-side-stores.md).

The migration unit is a logical store, not a directory or filename extension. For example, a workflow node can put its checkpoints into the same database.sqlite that an old application used. A PostgreSQL application can also have a local operator binding, a Git repository of flow versions, and an agent runtime with its own databases. Removing the volume after migrating ETL would lose data. [Issue and agreed scope](https://github.com/cuttlely/cuttlely/issues/516)

## Empty-disk recovery audit

The replacement test starts with three installations: fresh PostgreSQL, existing PostgreSQL with local side stores, and SQLite migrated to PostgreSQL. It signs in and exercises a saved flow, removes the original application directories, and starts a replacement web process and worker with the same durable configuration. The replacement signs in, runs a prediction with a synthetic model, uses a saved credential for a real read-only PostgreSQL tool call, and reads its attachment. All three cases passed locally and on a disposable Render service with a separate managed database. The hosted fixture used independent web and worker processes in one service. [Replacement fixture](../../scripts/storage-replacement.test.mjs)

Recovery starts after verified cutover. If the sole source disappears between the SQLite application copy and side-store migration, restore the original files and key from backup. Keep every PostgreSQL schema in the backup. Active writers, insufficient privileges or space, an incompatible target and verification mismatches require operator action.

| Finding                                                 | Mitigation and verification                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Legacy ETL file missing after replacement               | Owned legacy files are copied and retain their incremental identities. A missing source names the file to re-upload. New ETL panel uploads use PostgreSQL. [ETL recovery test](../../packages/etl/check/upgrade-control.test.mjs)                                                                           |
| Local application uploads or attachments                | The web server and workers bind to the same PostgreSQL file store after cutover. With S3, legacy local files must match the bytes at the target keys. An absent or different object blocks cutover. Record the external bucket in the backup plan. [File migration](../../packages/etl/migrate-uploads.mjs) |
| Missing settings flag or partial PostgreSQL restore     | Startup checks the durable settings and migration markers. A missing control row or required table stops startup. Restore the full database, correct key and host boot settings. [Startup checks](../../packages/etl/storage-upgrade.mjs)                                                                   |
| Older flow versions or disconnected Git synchronization | PostgreSQL retains authoring history, named refs, sync receipts and connection settings. An empty checkout is reconstructed and can restore a historical revision. [History recovery test](../../scripts/storage-copy-application.test.cjs)                                                                 |
| Analyst workspace or runtime session lost               | A new SQL query provisions the Analyst workspace. Rerun the flow that populated it. A replacement can recover committed runtime session history. In-progress turns can require a retry.                                                                                                                     |

### Additional dependencies found in source

-   **Migration window.** The SQLite application copy and the side-store cutover are separate operations. The primary copy requires an empty destination and the supported source schema. Preserve the original key, application files, custom settings and all SQLite stores together before any deploy that replaces the original instance. Resume and rollback use source files and checksums. Keep an off-host restore copy through the rollback window. The cutover pauses for active writers, other members, insufficient disk space or privileges, conflicting source copies and failed verification. Existing PostgreSQL installations can still have local side stores. A fresh application whose schema migrations completed before storage activation can also enter the existing-install path on retry. [Operator procedure](../how-to/postgres-side-stores.md)
-   **Host identity and startup.** A replacement needs the PostgreSQL connection and TLS material, storage selection and original installation key on every applicable process. A rotated installation also needs its active credential generation. A separate settings database, external object store or Redis queue needs its own durable service and host configuration. Changing the database connection fingerprint can require host proof to recover instance-operator administration. The host still needs writable scratch space for Git, runtime profiles, staging and logs. [Key verification](../../packages/server/src/settings/keyGuard.ts) · [Operator binding](../../packages/server/src/identity/instanceOperator.ts)
-   **External workers.** The harness worker and BullMQ worker bind the application stores before accepting work. An empty-disk fixture signs in, runs a credential-backed prediction, opens the saved SQL credential from an independent worker process, calls the SQL tool, and reads a stored attachment.
-   **Workflow and runtime inputs.** Live and draft graphs and stored ETL versions report external file inputs. Supply immutable files with the deployment and verify their manifest on each instance. Move mutable stores to an appropriate service or retain their volume. Plugins with unknown dependencies stop cutover for operator review. Operator-authored tool code may compute additional paths and needs a representative run. [Operator options](../how-to/postgres-side-stores.md#operator-supplied-files)
-   **Analyst.** The first new query provisions an isolated PostgreSQL workspace. Rerun the analysis to rebuild SQLite working tables. Retain existing PostgreSQL credentials, their encryption key and role permissions.
-   **Versioning and exports.** PostgreSQL restores main, secondary named refs, GitHub connection and environment settings, and sync receipts. An authenticated download route serves chat export attachments on object storage. Retain external logs separately if required. [Version recovery](../how-to/postgres-side-stores.md#recover-earlier-flow-versions)
-   **Deployment evidence.** Run the replacement fixture on fresh PostgreSQL, an existing split installation, and an offline SQLite copy. Each must recover the same login, workflow and credential-backed service with empty application and worker directories. The checked-in production Blueprint uses a persistent disk. The hosted gate uses a separate disposable project.

After the storage upgrade, the runtime commits session transactions to PostgreSQL. A replacement can recover acknowledged runtime messages. Pending deliveries and delegated results may still need a retry. Configurations saved through the runtime can be restored. A direct write from a host shell still relies on that host's filesystem.

## Reconcile an installation

Run the source and disk audits of [the inventory script](../../scripts/storage-inventory.py) from the checkout. Direct the CSVs to a private directory outside the inspected roots.

```sh
python3 scripts/storage-inventory.py source > "$audit_dir/source-evidence.csv"
python3 scripts/storage-inventory.py families > "$audit_dir/path-families.csv"
python3 scripts/storage-inventory.py disk "$data_root" "$additional_root" > "$audit_dir/local-files.csv"
```

Source mode indexes path literals and file/database API references in tracked implementation and deployment files with source locations. Families mode groups literal candidates by scope and lists the referencing source files. The evidence CSV preserves individual line numbers and writer operations for review. Test and fixture paths use a separate label where their naming identifies them. A reference can be a reader, example, restore path or writer. Dynamic destinations require inspection of the caller. Disk mode records every regular file, symlink and special entry under the explicit roots using metadata only. It includes hidden and extensionless files and does not traverse symlink targets. Inventory separately mounted targets explicitly. Collect a baseline and repeat after exercising each feature and restarting the processes. Paths alone cannot prove which process wrote a file, content parity or successful migration.

For overall upgrade testing use synthetic data in a separate disposable Render project. Provision the lowest-cost database and application resources suitable for the scenario, add a worker or disk only when needed and record their IDs at creation. Use independent secrets, volumes and databases. Delete the test project and all test resources after the run and verify their removal by those IDs. Exercise clean SQLite and PostgreSQL installs, an existing split-store upgrade, an interrupted copy and resume, rollback after a new write, an external worker, overdue schedules and a restart with the old files read-only. Reconcile each file against the store tables, local-retention policy or a named external owner; keep unrecognized files for investigation. Compare actual rows and content digests under a consistent snapshot. Verify unchanged embeddings, authorization and a real conversation after cutover. A clean data directory alone cannot validate an existing-install upgrade.
