# Disk storage inventory for the PostgreSQL upgrade

PostgreSQL hosts can move application-owned SQLite side stores from Server Settings. [Operator upgrade and rollback guide](../how-to/postgres-side-stores.md).

The migration unit is a logical store, not a directory or filename extension. For example, a workflow node can put its checkpoints into the same database.sqlite that an old application used. A PostgreSQL application can also have a local operator binding, a Git repository of flow versions, and an agent runtime with its own databases. Removing the volume after migrating ETL would lose data. [Issue and agreed scope](https://github.com/cuttlely/cuttlely/issues/516)

## Locate the roots first

| Root                 | Resolution and deployment implications                                                                                                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Application SQL      | The SQLite application driver resolves DATABASE_PATH/database.sqlite, with the user's .cuttlely directory as fallback. The PostgreSQL driver uses its configured database and schema. See packages/server/src/DataSource.ts.                                                   |
| Cuttlely data        | CUTTLELY_DATA_DIR, normally the checkout's .cuttlely for the harness package. Other packages have different fallbacks. Compose sets this to /var/cuttlely and sets DATABASE_PATH and SECRETKEY_PATH to /var/cuttlely/data. Enumerate both when overridden.                     |
| Server settings      | settingsDir() in packages/server/src/settings/store.ts resolves the settings directory. The saved-settings PostgreSQL connection has its own URL and allowlist. Selecting PostgreSQL for the application and selecting PostgreSQL for server settings are separate operations. |
| ETL                  | CUTTLELY_ETL_DIR or the etl directory under the Cuttlely data root. Local vector collections live under its vectors directory.                                                                                                                                                 |
| Agent profiles       | CUTTLELY_HERMES_HOME or the hermes directory under the Cuttlely data root. The Python runtime resolves its own HERMES_HOME and profile context. Walk the runtime root and every profile, including draft, Try, parked and recovery directories.                                |
| Secrets and versions | SECRETKEY_PATH or the user's .cuttlely directory for generated auth secrets. CUTTLELY_VERSIONS_DIR or the versions directory under CUTTLELY_DATA_DIR, falling back to the user's .cuttlely/versions. Preserve the hidden .git directory.                                       |
| Other mounts         | Include BLOB_STORAGE_PATH, LOG_PATH, absolute node inputs, user-supplied file outputs, external workers' mounts, and operator-configured plugin, browser and backup roots. Resolve container paths in the respective container.                                                |

SQLite also writes companion files named _-wal, _-shm and \*-journal, depending on journal mode and activity. Treat these and recovery or renamed copies as members of the same store. A live WAL can contain committed rows absent from the main file. Take a consistent SQLite backup or quiesce every writer before copying. Keep old and verified destination inventories for rollback.

## Reconcile an installation

Run the source and disk audits of [the inventory script](../../scripts/storage-inventory.py) from the checkout. Direct the CSVs to a private directory outside the inspected roots.

```sh
python3 scripts/storage-inventory.py source > "$audit_dir/source-evidence.csv"
python3 scripts/storage-inventory.py families > "$audit_dir/path-families.csv"
python3 scripts/storage-inventory.py disk "$data_root" "$additional_root" > "$audit_dir/local-files.csv"
```

Source mode indexes path literals and file/database API references in tracked implementation and deployment files with source locations. Families mode groups literal candidates by scope and lists the referencing source files. The evidence CSV preserves individual line numbers and writer operations for review. Test and fixture paths use a separate label where their naming identifies them. A reference can be a reader, example, restore path or writer. Dynamic destinations require inspection of the caller. Disk mode records every regular file, symlink and special entry under the explicit roots using metadata only. It includes hidden and extensionless files and does not traverse symlink targets. Inventory separately mounted targets explicitly. Collect a baseline and repeat after exercising each feature and restarting the processes. Paths alone cannot prove which process wrote a file, content parity or successful migration.

For overall upgrade testing use synthetic data in a separate disposable Render project. Provision the lowest-cost database and application resources suitable for the scenario, add a worker or disk only when needed and record their IDs at creation. Use independent secrets, volumes and databases. Delete the test project and all test resources after the run and verify their removal by those IDs. Exercise clean SQLite and PostgreSQL installs, an existing split-store upgrade, an interrupted copy and resume, rollback after a new write, an external worker, overdue schedules and a restart with the old files read-only. Reconcile each file against the store tables, local-retention policy or a named external owner; keep unrecognized files for investigation. Compare actual rows and content digests under a consistent snapshot. Verify unchanged embeddings, authorization and a real conversation after cutover. A clean data directory alone cannot validate an existing-install upgrade.
