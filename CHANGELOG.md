# Changelog

This file records every notable change to Cuttlely. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Cuttlely uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). [Releases and support](./docs/releases.md) explains what counts as a breaking change and which versions get fixes.

## [Unreleased]

## [1.3.0] - Unreleased

### Added

-   **Run a harness from your app with an API key.** Each API key has a list of harnesses it may run, **Harnesses this key may run** in the API key dialog or `harnesses` on `POST` and `PUT /api/v1/apikey`. The list starts empty on every key, including keys made before this release, so a key runs no harness until one is ticked, and the refusal is the same `403` whether or not the harness exists. A key that creates or edits a key may grant only harnesses on its own list. A `harnesses` value that is not an array is `400`, and an edit that sends back a name whose harness is gone drops it. `POST /api/v1/harnesses/:name/runs/async` answers `202` with a run id, and `GET /api/v1/harnesses/:name/runs/:runId/result` returns the status and, once the run is done, the full answer. The run uses the published harness and shows under **Runs** as `api`, with the same run card, tokens, usage totals and traces as any other run. Each key, or each signed-in person, may start 60 runs (both run routes together) and read 600 times a minute (the run list, a run, and a result), counted in each server process. A key lists and reads only the runs it started, and a `chatId` that already has runs from another caller is refused with `403`. A restart or shutdown waits for a background run. At the next start, a run still queued or running that began more than the turn lock time plus 15 seconds earlier is marked failed with `interrupted`; a newer one is left to the process that may still own it, and is closed the same way that long after the start if it is still open. [Run it from your app with an API key](./docs/how-to/harnesses.md#run-it-from-your-app-with-an-api-key), [Run a harness in the background](./docs/api.md#run-a-harness-in-the-background).
-   **Run a harness on a schedule.** **Schedule** on the harness page takes a five-field cron, a time zone and the question for each run (`PUT /api/v1/harnesses/:name/schedule`, with pause, resume and delete routes). Day of month and day of week follow Vixie cron, a range needs exactly two ends (`1-2-59` is refused), and when the day-of-week field starts with `*`, a day of the month no chosen month has (`30 2`) is refused. The time zone is a place name such as `Europe/Paris`, or `UTC`; offsets and abbreviations are refused. A schedule runs Live with the permissions of the person who last saved or resumed it, checked again at each due time; a due time whose owner can no longer run the harness is recorded as `refused`. An API key can read a schedule for a harness on its list, with the owner's name only and the question redacted, and cannot change one: the save, pause, resume and delete routes refuse a key with `403` whatever the path spelling. Those writes are limited to 30 a minute per person. When the clocks spring forward over a fixed time, the schedule runs at the first minute after the change, as Vixie cron does; a `*` minute or hour schedule skips those minutes. When the clocks fall back, each wall time in the repeated hour runs once. A due time while the previous scheduled run is still going is skipped. Schedules are kept in the harness database, continue after a restart, run a missed due time once, start only after the server has started cleanly, and start nothing while a server restarts or shuts down: Restart stops the schedule timer as soon as it is accepted, and waits for a scheduled run that already started. A due time still starting after a minute shows as failed. **Delete schedule** asks first. Servers sharing the data claim each due time once. Scheduled runs show under **Runs** as `schedule`. [Run it on a schedule](./docs/how-to/harnesses.md#run-it-on-a-schedule), [Schedule a harness](./docs/api.md#schedule-a-harness).
-   Audit log types `harness_run` (a background run started with `POST /api/v1/harnesses/:name/runs/async`, or a harness run an API key was refused because the harness is not on its list), `harness_access` (a change to a key's harness list), and `harness_schedule` (schedule changes, every scheduled run start with its run id, and refused scheduled runs). [Audit API](./docs/reference/audit-api.md).
-   **Tables and views** on the PostgreSQL MCP node lists the connected database's tables, views and materialized views, materialized views first, then views, then tables, with a checkbox each. With any ticked, the analyst gets one line per ticked relation (name, kind, up to 12 column names, comment) instead of a schema in its instructions, a new **describe** tool returns one relation's columns, keys, relationships among ticked relations and view definition, and the server refuses a query that reads anything else, calls a function, operator or type outside `pg_catalog`, calls a built-in that reaches other data or reports on other objects, or is not a read. A query that fails on an undefined or ambiguous column gets the column list of each ticked relation it names in the error. A database with a domain whose `CHECK` calls a volatile function, a function outside `pg_catalog` or a denied built-in refuses every scoped query, naming those domains, because such a check can run while a statement is parsed. It is tested against Postgres 14 to 18. Postgres checks each statement through a temporary view in the query's own transaction before it runs read only, so the credential needs `TEMP` and a read replica refuses queries while a selection is set. Nothing ticked keeps the old behavior. On the bakery demo database the analyst's prompt drops from 2,562 to 663 tokens. [Pick the tables and views the analyst sees](./docs/how-to/analyst.md#pick-the-tables-and-views-the-analyst-sees), [Analyst tools](./docs/reference/analyst-tools.md).
-   A harness can have several analyst specialists. Harness Prime is told which tables each analyst has ticked and sends a database question to the analyst that fits, or to each one that fits. When the router returns no steps for a database question, one more short route call chooses among the analysts, and a choice it cannot use sends the question to every analyst instead of the first one. `show more` pages the analyst that returned the result. The dialect note is one line per analyst. With one analyst the prompts are unchanged. **describe** also returns up to 10 sample values for short text columns with few distinct values, from the described relation only, and every analyst is told to check distinct values or use `ILIKE` before reporting zero rows for a text filter. [Several analysts in one harness](./docs/how-to/analyst.md#several-analysts-in-one-harness).
-   **Rules** on the PostgreSQL MCP node, under **Tables and views**: a box for your own instructions to the analyst, such as which view answers which question or how names are written. The analyst gets them word for word at the end of its instructions, between `<analyst_rules>` tags, and an empty box adds nothing. Cuttlely adds no rules of its own. Rules cannot widen the table selection or allow writes: Postgres still refuses a query that reads an unticked relation, whatever the rules say. The box takes up to 2,000 characters with a counter under it, the Expand editor shows the same counter, and saving a harness refuses longer rules, from the canvas, **Import JSON** or the draft API. Rules from several PostgreSQL MCP cards on one analyst count together and are refused, not cut, when they pass the limit. Restoring, rolling Live back to, or promoting a version whose rules are over the limit is refused with 400 and changes nothing. That includes a version that already matches Live, which would otherwise be reported as unchanged; the message then says first that Live, or for a Restore into a draft the draft, is unchanged. Only a card wired straight to the analyst counts; rules on a card wired into another node are ignored. Rules are saved, exported and imported with the flow. Harness Prime does not get them. The node version is 1.3. [Write your own rules](./docs/how-to/analyst.md#write-your-own-rules).
-   `pnpm verify` ends with a timing table of the steps that ran, slowest first, with each step's time and share of the total. It prints on a pass and on a failure, and pass or fail is unchanged.
-   A media size check (`scripts/media-size.mjs`) fails when a tracked or staged image or video file is over 5 MB and is not listed in `scripts/media-size.allowlist`. The allowlist holds the large website videos already committed. It runs as a `pnpm verify` step, including `--fast` and the pre-push hook, and in the required `lint` CI job.
-   `CUTTLELY_OTEL_TRACES_CONTENT_MAX` sets how many characters of question, answer, prompt, and tool text each run trace span keeps when `CUTTLELY_OTEL_TRACES_CONTENT` is on. The default stays 4,000, so existing installs see no change. `0` is no limit and sends the full question and answer text to your OpenTelemetry collector, so use it only with a collector you trust. It is **Prompt and tool text limit** under **Admin** > **Server Settings** > **Integrations** > **Traces**, with **Default (4,000 characters)**, **No limit**, and **Another limit**. The page refuses anything that is not a positive whole number or `0`. A host value that is not a whole number keeps 4,000, and the server logs one warning about it at startup. [Run traces](./docs/how-to/observability.md#full-question-and-answer-text).
-   A Grafana dashboard for run traces and server metrics, `metrics/grafana/cuttlely-runs.json`. It reads traces from Tempo and `GET /api/v1/metrics` from Prometheus, with rows for runs, latency, tokens and an estimated cost from input and output price variables, errors, each flow and harness, and the Prometheus server metrics. [Run traces](./docs/how-to/observability.md).
-   Japanese and Korean READMEs (`README.ja.md`, `README.ko.md`). The English, Japanese, Korean and Chinese READMEs link to each other with an English | 日本語 | 한국어 | 繁體中文 | 简体中文 switcher, and the older `i18n/README-JA.md` and `i18n/README-KR.md` point to the new files.
-   The benchmark whitepaper is on the website at `/whitepaper/`, as a web page and a PDF.

### Fixed

-   Deleting an ETL pipeline whose Local Vector Store has a blank Collection field now removes its vectors from the collection of every name the pipeline ran under. Before, a pipeline whose name changed and that ran again left the vectors in the collection under its old name. A paused run resumed after the name changed now writes every chunk to the new collection, instead of splitting them across both and failing the store count check.
-   A publish check whose last answer or grade is cut off by the check's time limit now ends stopped for time instead of done. Before, it could end done and, for a dataset check, store a verdict scored with that cut-off grade as Error. Now no publish gate result is stored for that check, so it cannot unblock Publish, and the next check runs as usual.
-   **Prompt and tool text limit** lists the 4,000-character default once, as **Default (4,000 characters)**, instead of also offering a separate **4,000 characters** item. A saved value of 4000 shows as that default item.
-   Docs: the Docker commands that create the first account or run `pnpm settings` name the `cuttlely` Compose service, and the first-account command sets `CUTTLELY_LOCAL_ADMIN=true`, which the command needs to create a user. The translated READMEs have the same fix.
-   Docs: the in-page links in the Japanese and Korean READMEs work on GitHub. The version examples in the `cuttlely` package README, the Docker guide and the embed guide name 1.3.0. The READMEs describe **Tables and views**, the `describe` tool and several analysts in one harness, and the home page Analyst callout also gives the two-analyst run (9 of 9). The English, Japanese and Korean READMEs follow the home page's section order: the demo, A/B testing, made for real teams, agent teams, the API, small context, tools, then getting started. The Chinese READMEs keep a shorter structure of their own. Every table-of-contents link resolves on GitHub. The home page and the Analyst guide no longer say each data question was answered on its first query.

### Security

-   A harness run always names its caller: a signed-in person (checked by role), an API key (checked against its harness list), or a flow with no key. A call that names none is refused. A chatflow or agentflow bound to an API key runs its Harness cards and Agent harness tools only for harnesses on that key's list when it runs without a person: the prediction API, a webhook, its MCP endpoint, or its schedule. The in-app chat and Try it run them for the signed-in person. With an API key, a harness canvas off the key's list answers `403` on the chatflow, draft, publish check, version history, flow config, chat message, stats and schedule status routes, and on `GET /api/v1/chatflows/has-changed/:id/:time`, and is left out of `GET /api/v1/chatflows` and of `GET /api/v1/chatflows/apikey` for the key it names. The Harness card's picker (`POST /api/v1/node-load-method/harness`) lists only the key's harnesses. Names are read from the parsed canvas, so a key written with a JSON escape (`harness\u004eame`) is checked like any other. A key cannot save, publish, roll back, restore or promote a canvas that names a harness off its list anywhere in it, or change a flow's key while that flow names one. A harness name in a canvas must be text with no surrounding spaces; any other value is `400` on every save. The publish check replays each question for the caller that started it. [Run a harness in the background](./docs/api.md#run-a-harness-in-the-background).
-   With an API key, a flow's MCP server settings (including reading its token), its webhook secret, and its schedule switch answer `403` unless the flow is bound to that key or to no key and every harness it names is on the key's list.
-   `POST /api/v1/internal-prediction`, the in-app chat that runs the draft, refuses every API key with `401`, in the gate and in the route itself.
-   Deleting a harness (`DELETE /api/v1/harnesses/:name`) removes it from every key's harness list first, in one transaction, then removes its schedule, then the harness. If either step fails the delete answers `500` and the harness is kept, so a new harness with the same name never inherits the old key grants or schedule. [Delete a harness](./docs/api.md#delete-a-harness).
-   `GET /api/v1/chatflows/apikey` and `GET /api/v1/verify/apikey` read the API key from the `Authorization: Bearer` header. The older form with the key in the URL path (`/chatflows/apikey/<key>`, `/verify/apikey/<key>`) now answers 400 and does not check the key, because proxies, browser history and access logs keep URLs.
-   A Code Repository source refuses a branch that starts with `-`, and its git clone and fetch end options with `--`, so a branch or URL can never reach git as an option such as `--upload-pack`.
-   The sign-in (`/api/v1/auth`, `/api/v1/account`), API-key check (`/api/v1/verify`), OAuth credential, custom MCP server and node and credential icon routes are rate limited per client with the UI page-load budget (**Page loads a minute**, `CUTTLELY_UI_PAGE_LIMIT_MAX`, 3000 by default). Each router has its own count. A client over the budget gets 429. The node and credential icon routes add three times the number of loaded nodes or credentials to that budget, because the node palette and the credential dialogs ask for every icon at once, so a cold palette load does not get 429 at the lowest setting (100). Node and credential icons are sent with `Cache-Control: public, max-age=86400`, so a browser asks for each one at most once a day.
-   A `feedbackType` query value that is not a string or a list of strings is ignored instead of being passed on. `GET /api/v1/stats/:id` no longer answers 500 with the error object for such a value. Clearing chat messages (`DELETE /api/v1/chatmessage/:id`) with a `feedbackType` that names no known rating answers 400 instead of clearing every message.
-   The uploaded-file download refuses a repeated `chatflowId`, `chatId` or `fileName` with 400.
-   The `/api/v1` sign-in gate compares the decoded request path with the public list and the list of routes an API key cannot use after collapsing repeated slashes and ignoring ASCII letter case, the way Express routes it. An API key is refused on those routes in every spelling Express serves. `DENYLIST_URLS` entries are compared the same way, with surrounding spaces ignored. `/api/v1/chatflows/apikey/` and `/api/v1/verify/apikey/` are public for GET and HEAD only. Run counting for Restart and shutdown matches the decoded run path the same way.
-   An evaluation run refuses a chatflow id other than 1 to 64 letters, digits, `_` or `-` before it posts, and puts the id in the prediction URL encoded as a path segment.
-   Text parsing that code scanning reported as slow regular expressions now runs in linear time: the chat widget's host and link base, ETL number, JSON and whitespace handling, quota error detection and collection names, and in harnesses the analyst statement fingerprint, keyword connection strings, upload stubs, pin lines, closing source lines, numbered task lists and arithmetic questions. Answers are unchanged, with one exception: the first-run owner email is refused when a domain label is empty (`rosa@bakery..example`, `rosa@bakery.example.`).
-   Code scanning uses a CodeQL advanced setup (`.github/workflows/codeql.yml`) for GitHub Actions, JavaScript and TypeScript, and Python, and the repository's default setup is off. It skips the pinned upstream copy in `hermes/`, whose security releases are tracked weekly, and scans the `hermes/` files that Cuttlely's own patches touch in a separate Python analysis. Dependabot updates the workflow's pinned actions weekly. [Hermes upgrades](./docs/reference/hermes-upgrades.md#code-scanning).
-   Rating a message (`POST /api/v1/feedback`, `PUT /api/v1/feedback/:id`) and uploading a chat attachment (`POST /api/v1/attachments/:chatflowId/:chatId`) accept a signed-in session only with `x-request-from: internal`, which the app sends on every request and a cross-site form cannot. Without it the flow's API key decides as before, so embedded chats and keyless flows are unchanged.
-   A harness no longer compiles a tool schema's `pattern` as a regular expression, because the pattern can come from any MCP server and a backtracking pattern could stall the harness on short input. A one-field tool whose schema has a `pattern` now gets its arguments from the model instead of taking the typed text directly. A JSON object of the tool's fields is still taken as typed. When a model without native tool calling picks such a tool with a bare string, it is asked to send a JSON object of the field. No shipped tool is affected: the two that declare a pattern have more than one field.
-   The release script treats a CHANGELOG section that is only HTML comments as empty even when one comment hides inside another. The website build check drops a `<script>` or `<style>` block whose end tag has spaces or attributes, and decodes `&amp;` in a link once. The docs description text and the Pipedream user id strip tags until nothing changes. These clear the code-scanning results that had a code fix; the rest are dismissed with reasons in the pull request.
-   An invited person joins only through their own invite link. Before, a pending invite who signed in with AuthKit using a verified matching email was made active without the link. Now a new invite is stored as `invited`, and with AuthKit on it always returns or emails a one-time invite link (Add User shows it once). `/local-accept` offers **Accept invite with WorkOS**, which carries the token through AuthKit in a 15-minute httpOnly cookie (`POST /api/v1/auth/invite/start`). The callback activates the person and binds that AuthKit sign-in only when the token is unused, unexpired, made for that person and that email, and the invite still stands. An email match alone shows `You have a pending invite. Open the invite link from your email to join.` and leaves the person pending with no team access. With AuthKit on, `POST /api/v1/auth/local/accept` refuses an invite token, so a password cannot stand in for the AuthKit sign-in. `workspace:add-user` can send the invite link for an invite into the caller's own active team. Removing a pending person from the team or the organization, disabling them, or issuing a newer link (`POST /api/v1/users/:id/reset-link` now issues an invite link for a pending person) makes the old link invalid, and enabling a user never activates a pending invite. Active users sign in as before. A user created by an invite before this change, who has never signed in, is still stored as `active` and can still join by email match; remove and invite them again to require the link. [Invite people](./docs/how-to/sign-in.md#invite-people).
-   A raw MCP server listed in a specialist record's `mcpServers` now passes the same checks as a Custom MCP node (`CUSTOM_MCP_ALLOWED_COMMANDS`, `CUSTOM_MCP_ALLOWED_ABSOLUTE_SCRIPT_PATHS`, `CUSTOM_MCP_ALLOWED_ENV_VARS`, no `cwd`, no shell characters, no code-running flags) before the agent runtime starts it. One that fails is left out of the profile with a warning in the server log. `CUSTOM_MCP_SECURITY_CHECK=false` turns the checks off, as it does for the node.

### Upgrade notes / breaking changes

-   **API keys need their harnesses ticked.** An API key that calls `POST /api/v1/harnesses/:name/runs`, reads that harness's runs, or reads, saves or deletes the harness by name, now also needs the harness under **Harnesses this key may run**, and gets `403` `This API key may not run harness "<name>".` otherwise. Before, the role permission was enough. The same goes for a chatflow or agentflow bound to a key whose Harness card or Agent harness tool names a harness: that card fails until the harness is ticked on the flow's key. After upgrading, edit each such key and tick its harnesses. At startup the server logs each bound key that is missing a harness its flow names.
-   **Known limits of the harness list.** A flow with no API key still runs every harness it names, in its team, for anyone who has its id. Execute Flow, Chatflow Tool and Agent as Tool send the API key stored in their credential, so the flow they call runs under that key's list, whoever can use the credential: keep keys that list harnesses out of shared credentials. [Known limits](./docs/api.md#known-limits).
-   **Flow config needs a permission.** `GET /api/v1/flow-config/:id` now needs `chatflows:view`, `chatflows:update`, `agentflows:view` or `agentflows:update`; before, it checked none.
-   **Draft chat refuses API keys.** `POST /api/v1/internal-prediction` now answers `401` to every API key. An app uses `POST /api/v1/prediction/:id`.
-   **Database changes for harnesses.** At startup the app database adds a `harnesses` column to the API key table (migration `AddApiKeyHarnesses`), empty on every existing key, and the harness database adds a `harness_schedules` table.
-   **API keys are no longer accepted in a URL.** `GET /api/v1/chatflows/apikey/<key>` and `GET /api/v1/verify/apikey/<key>` now answer 400 without checking the key. Send the key as `Authorization: Bearer <key>` to `GET /api/v1/chatflows/apikey` or `GET /api/v1/verify/apikey` instead. A client or script that still puts the key in the path breaks until it is changed. Once it is, consider rotating any key that was sent in a URL, because proxy and access logs may still hold it.
-   **Rate limits on sign-in and a few other routes.** Sign-in, the API-key check, OAuth credentials, custom MCP servers, and node and credential icons now answer 429 past **Page loads a minute** (`CUTTLELY_UI_PAGE_LIMIT_MAX`, 3000 by default) per client address. Behind a reverse proxy, set `TRUST_PROXY` before you upgrade, or every client shares one count and sign-in can be blocked for everyone. [Server settings](./docs/how-to/server-settings.md).
-   **Raw MCP servers on specialist records.** A raw entry in a specialist's `mcpServers` (one that is not an MCP node connected on the canvas) now starts only if its command is in `CUSTOM_MCP_ALLOWED_COMMANDS` and its script path is in `CUSTOM_MCP_ALLOWED_ABSOLUTE_SCRIPT_PATHS`. Both are empty by default, so every such server is refused until you set them. A refused server is left out of the harness, and the server log has a warning that names it. If `packages/components` is not built, every raw server is refused. Before you upgrade, set those allow-lists (and `CUSTOM_MCP_ALLOWED_ENV_VARS` for any `env` the server passes), or set `CUSTOM_MCP_SECURITY_CHECK=false` to keep the old behavior.
-   **Pending invites need their invite link.** An invited person now joins only through their own one-time invite link: it is single use, expires (72 hours by default), works only for that person and the email it was sent to, and stops working when a newer link replaces it or the person is disabled or removed from the team or the organization. A sign-in whose email matches a pending invite never activates it, even with a verified email, and shows `You have a pending invite. Open the invite link from your email to join.` An invite link issued before the upgrade keeps working until it expires: without AuthKit it still sets a password, and with AuthKit on it is used through **Accept invite with WorkOS**, not a password. A user already stored as `invited` before the upgrade can use such a link; otherwise make one with `POST /api/v1/users/:id/reset-link` and send it. A person added with **Add User** before the upgrade was stored as `active`, not pending, and can still join by email match; to require the link, remove them and invite them again. With AuthKit on, every new invite returns or emails a link, and **Add User** shows it once. [Upgrading](./docs/upgrading.md#invites-after-130).
-   **Database changes.** At startup the ETL database moves to schema version 4 and gains a `run_names` table, which records the pipeline name each run ran under. Each run that started before the upgrade is recorded under the pipeline's name at upgrade time. Vectors written under a name the pipeline had before it was renamed, before the upgrade, are not removed when the pipeline is deleted.

## [1.2.0] - 2026-10-15

### Added

-   An audit log for sign-in success and failure, lockout, invite, reset, role change, user disable, and settings changes. `GET /api/v1/audit` is for the organization owner or `audit:view`. Passwords, tokens, secret values, and question text are not stored. Rows older than `CUTTLELY_AUDIT_RETENTION_DAYS` (90, from 1 to 3650) are left out. The setting is off until it is turned on, and stores a dataset, its evaluators and a pass mark from 0 to 100. A thumbs-down row leaves the expected answer empty and marks it as needing one. A message already in the dataset is skipped, and one add writes at most 500 new rows. -   Harness runs can send OpenTelemetry traces, with the same switch and attribute names as chatflow and agentflow runs. `harness.run` is the root, with a span for the route, each specialist, the handoff, each in-process model call and each tool call. A harness run from a chatflow Harness node is nested under that chatflow's trace. A canvas draft try and a Publish check replay send nothing. ## [1.0.0] - 2026-10-10

The first Cuttlely release. It covers everything on `main` up to the release tag.

Cuttlely is the open-source agent platform for applications: build an agent team on a canvas or from a description, chat with it in minutes, and call it from your app through the API. The README and docs lead with that, with a real API call to a small team and the chat-first path for newcomers.

### Harnesses

-   Build agent teams on the harness canvas. Harness Prime reads the question, routes each part to a specialist using a short summary of each one, and writes one answer. A chatflow calls the whole team by name.
-   Specialists run in the agent runtime that ships with Cuttlely and starts with it on the same server. Each turn starts a fresh session, and follow-up questions still work. Specialists get their tools directly, load playbooks only when needed, and their instructions name each playbook.
-   Harness Prime reads up to 4,000 characters of each specialist answer, and it sees images attached to the turn. Images a specialist writes during a turn show up in the chat.
-   A step can wait for an earlier step and use its result.
-   The run card shows the route, each specialist, and the tokens in and out. Specialist tokens count toward the turn total, and cached prompt tokens are shown separately.
-   Build with AI on the harness canvas: describe your team and a first version lands on the canvas.

-   Charts and other images a team makes also show up in the harness canvas chat.
-   A question asked while the agent runtime is still starting waits for it, up to a minute (`CUTTLELY_HERMES_START_WAIT_MS`), instead of failing with "Hermes did not accept POST /v1/runs".

-   A read-only analyst fixes a failed SQL statement once by itself. The SQL dialect follows the PostgreSQL credential on its card.
-   A 15-second statement timeout applies to every analyst call, on Postgres and on SQLite.

### ETL pipelines

-   Pipelines load files, a CSV or a code repository, then clean, split, embed and store the data for search. A run embeds only what changed and can run on a schedule. Local embeddings need no provider key.
-   Harnesses and chatflows search a pipeline's output with the **ETL Retriever**.
-   Deleting a pipeline also deletes the vectors it wrote.
-   Build with AI on the ETL canvas: describe your data and a first pipeline lands on the canvas.

Every model list also takes a typed model name, so a flow saved with a model that has left the list still opens and runs with it. Cards for servers you run yourself, such as Ollama, LocalAI, LiteLLM and OpenAI Custom, keep a plain text field.
-   Claude Sonnet, Haiku, Fable and Mythos 5 and later get no temperature, top P or top K, which those models refuse, and the Anthropic card offers adaptive thinking and effort on the Claude 5 models. GPT-6 models are treated as reasoning models on the OpenAI and Azure OpenAI cards.
-   Bring flows from other tools with a checked import wizard, from the **Import** menu on Chatflows. See [Bring your existing flows](./docs/bring-your-flows.md).
-   **Deprecated:** the OpenAI, Azure OpenAI and Cohere LLM (text completion) cards no longer appear in the node list for new flows, not even when searched by name, because those providers no longer offer a completion model. Flows that already use one still open and run as before. For new flows, use the chat model card of the same provider. Other deprecated cards show again when you search their exact name.

### Build with AI

-   On the chatflow, harness, ETL and workflow canvases, describe what you want and a first version lands on the canvas. Every part and connection is checked first, problems get one repair round, and credentials are matched by name. The building model is one of your own credentials.
-   Build with AI starts on a model you have a key for, with your key picked when only one fits. The list shows models for your keys first, and advanced settings wait under **More settings**.

### Versioning, Publish and Dev to Prod

-   Version history is on by default. Each save records what changed and who changed it, with diff colors and secret-looking text hidden. Restore a version, or open it as your draft. `CUTTLELY_VERSIONS=off` turns history off.
-   Drafts are on by default for chatflows and agentflows. The canvas saves to a draft. The API, embeds, shared links, schedules and webhooks keep serving Live until you publish. History shows Published markers and offers **Roll back Live**. `CUTTLELY_DRAFTS=off` turns drafts off.
-   The Publish check runs up to 10 recent questions on Live and on the draft and shows the answers side by side, with the tokens and time each took. It works on chatflows and on agentflows that start with a chat message.
-   Keep a copy of every version in a GitHub repository, from Admin, Version History. First-run setup goes straight into the app; it does not stop at a GitHub page.
-   Dev to Prod: Prod reads what Dev published, shows what would change and which credentials it needs, can run the same check, and goes Live only when its owner selects **Promote to Live**.

### Install and operations

-   A published Docker image, `ghcr.io/cuttlely/cuttlely:X.Y.Z` and `:latest`. Compose pulls it by default and builds your checkout when it cannot pull. The image reports its health from `/api/v1/ping`.
-   `npx cuttlely` starts that image. The `cuttlely` package is a Docker launcher, and `@cuttlely/chat` is the embeddable chat widget. The server stays in the image.
-   The Docker image runs on Debian trixie with Node 24. It runs as the `node` user and keeps its data in `/var/cuttlely`. Compose passes `CUTTLELY_VERSIONS`, `CUTTLELY_DRAFTS` and `CUTTLELY_ANALYST` from `.env`.
-   A Render Blueprint runs one container with Postgres.
-   From source on Node 24 with pnpm.
-   Sign in with a local account, or with WorkOS AuthKit for a team. On a fresh install the server log prints a one-time setup link, so the first account can be created in the browser, including through Docker's published port.
-   One process and SQLite by default. Harness turns use a SQLite queue in the web process.
-   **Server settings, Restart**: a full-screen view follows the restart (saved, runs finishing, stopping, each start-up step, back). When chats or agent team runs are in progress, Restart asks whether to let them finish (up to the turn time limit) or restart now; new runs wait meanwhile. The manual restart steps have a copy button.
-   **Server settings, safe boot**: a start that can't open the database after a settings change stops (exit 76) instead of running half-started, the start script starts it again, and its settings never become the last good copy, so the third start puts back the settings that worked. The restart screen shows that outcome as **The new settings did not start**. `pnpm verify` checks it on the real server (`pnpm safeboot:check`). When the start script (Docker, Render, a source install) does the rollback, it now tells the server, so the safe boot banner and that restart screen outcome show there too.
-   **Server settings guide** ([docs/how-to/server-settings.md](./docs/how-to/server-settings.md)) with real screenshots. Polish: high-risk changes need RESTART typed in the review; the safe boot banner has See what changed and Try it again; All settings has Copy as .env (secrets left out); queue mode reminds you to restart the workers; Switch database warns about the encryption key for a database that already holds Cuttlely data. On a phone the sections sit in one sideways row and the save bar fits; dialog buttons are in sentence case; setting names and the search field read clearly in dark mode. The page always keeps room for the save bar: it scrolls fully clear of it, and a field you move to never ends up under it. The sidebar marks the page you are on, also when you open it from an address, a link or the back button, including the pages under Admin.
-   **A one-time setup link when nobody can sign in**: a server with no account, the password sign-in off and no AuthKit (for example Render without the WorkOS values) prints a link in its log that opens only Sign-in & identity. Create the owner with a password, or set up AuthKit after a test sign-in with the owner email. The link works once and stops working once the first account exists. When accounts exist but no sign-in method is on, the browser shows the Sign In page with Sign-in is not configured instead of an empty page, and the log says how to turn one back on.
-   **Health check knows about the database**: while Cuttlely can't reach its database, at startup or later, `GET /api/v1/ping` answers `503` with a plain reason (for example `database unreachable: connection refused`), so Docker shows the container unhealthy and Render keeps a deploy without its database from going live. The log has one line naming the host and port, never the password, and Cuttlely never says it is ready without its database. Ping answers `pong` again once the database does.
-   **Server settings, Set up your server**: three optional first steps at the top of Server settings (sign-in for your team, the analyst, a model key), each opening the same section. Skip for now hides them.
-   **Server settings, Switch database**: SQLite or Postgres from the Database section. The new database is always tested first (sign-in, can create tables, empty or Cuttlely data already, other tables refused), the dialog says how the owner gets back in afterwards, the switch needs RESTART typed, and the previous database is kept for Switch back. Data is not copied.
-   **Server settings, Set up AuthKit**: a four-step guide in Sign-in (WorkOS key and Client ID with Staging or Production detected from the key, redirect addresses filled in with copy buttons, Generate seal, first owner email), then a real test sign-in with the values on screen, bound to the owner's browser session, before anything is saved. Password sign-in cannot be turned off until a test sign-in with the exact AuthKit values passes.
-   **Server settings, Test connection**: Analyst, File storage and Models each have a Test connection card that tries the values on the page before you save (Postgres sign-in and read-only check; S3, Google Cloud or Azure find, write and remove a small test file; the model list is fetched and checked). Errors come back in plain words, never with a secret in them.
-   **Admin, Server settings** (owner only): sign-in, database, agent runtime, analyst, models, storage, security, integrations and advanced settings in one page, with search, plain-language help, a review step before saving, Locked for values set where Cuttlely is installed, All settings, and History. Secrets are write-only. Changes apply at the next restart.
-   `scripts/start-cuttlely.sh` restarts the server in place when it exits with code 75, which is how Server settings applies a change. Safe boot puts back the last settings that started after two starts in a row that did not finish, and `pnpm settings list|unset NAME|restore` is the way back in from a terminal. [Upgrading Cuttlely](./docs/upgrading.md) has the details.
-   `pnpm verify` is the local merge gate.
-   Upgrades are tested. The full `pnpm verify` starts the current server on data written by an older Cuttlely and checks that flows, version history, credentials and harnesses survive (`pnpm upgrade:check`). [Upgrading Cuttlely](./docs/upgrading.md) covers backup, upgrade and roll back.
-   Model dropdowns and prices come from a model list the Cuttlely maintainers keep in this repository. A server fetches it from `main` at most once a day (5 second timeout) and uses the copy bundled with its build when that fails. `MODEL_LIST_CONFIG_JSON=bundled` turns the fetch off; a file path or URL replaces the list.
-   A quieter first start: the agent runtime skips about ten "Nous Portal not configured (run: hermes auth)" warnings, since Cuttlely never uses Nous Portal. Set `CUTTLELY_HERMES_NOUS_WARNINGS=show` to see them.
-   Start-up never looks stuck: the image build names each long step (1 of 4 to 4 of 4), the start script and server log each boot step, the log ends with `✅ Cuttlely is ready. Open http://localhost:43117`, and a browser opened during boot gets a **Cuttlely is starting** page that opens Cuttlely when it is ready. Ping answers `503` with `"status":"starting"` until then, so the Compose health check reads `health: starting`, then `healthy`. `CUTTLELY_STARTING_PAGE=off` turns the page off.
-   **Graceful shutdown**: on SIGTERM or SIGINT (what Docker and Render send on every stop and deploy), Cuttlely stops taking new requests, which get `503` with `Retry-After` (ping too), and lets running answers and streams finish for up to 25 seconds (`CUTTLELY_DRAIN_TIMEOUT_MS`). A run still going after that gets a `503`, or an `error` event with status `503` and code `UNAVAILABLE` on a stream, instead of a cut connection. A second signal stops at once. The Compose files give the container 35 seconds to stop.

### Security and API

-   The agent runtime makes no request to models.dev unless `CUTTLELY_MODELS_DEV=1` is set. `SECURITY.md` lists every host Cuttlely connects to and how to turn each off.
-   The API-key chatflow list returns only the flows bound to that key, and only their `id`, `name`, `deployed`, `category` and `type`.
-   Refreshing an OAuth credential needs a session or an API key with credential permissions.
-   Server settings (`/api/v1/server-settings`) are for the owner's signed-in session only. API keys are refused, secret values are accepted but never returned or logged (request bodies stay out of debug logs), and every save, discard and restart goes into the settings history.
-   Prediction errors keep their real status. A streamed `error` event carries `status` and `code`.
-   A model provider that keeps answering 429 is reported as `429` with `Retry-After` (the provider's wait when it sends one, otherwise 30 seconds), not as `500`, and within about 20 seconds instead of about 95: chat models and LLMs make at most 3 tries and start no new try after 20 seconds. A one-off 429 still recovers on the next try. A streamed `error` event also carries `retryAfter`.
-   A prediction with `Origin: null`, or an Origin that is not a URL, is refused.
-   Override configuration never takes a port from a request.
-   A request value never runs as code. In Multi-Agent and Sequential Agent flows, an allowlisted variable referenced in a code input is inserted as escaped text, so it reads as the same text inside quotes and cannot become code anywhere else (covered by tests, including an injection attempt).
-   Dependencies are on patched releases: `pnpm audit` reports no critical advisory and three high ones, none with a fixed release (two in Puppeteer's browser download, which Cuttlely skips, and `braces` in the command-line file matcher and in dev tooling). `expr-eval` is not installed: the older community package that depended on it is gone, and that package has no fixed release. The UI no longer installs Create React App (every UI script already runs Vite), and the server no longer installs a mail library it never used. Excel files are read with SheetJS 0.20.3, the fixed release SheetJS publishes on its own download site. The UI, agentflow and observe builds run on Vite 6.
-   The Docker image is built in two stages: the image you run has production packages only and no compilers.
-   Prediction uploads stay per chat. An image, audio or other file sent again with the same name, in the same chat or another one, is stored under a new name and never replaces an earlier file. Deleting a chat also removes the documents it sent, not only its folder.
-   Deleting a flow also deletes its leads (the name, email and phone people left in its chat), in the same step as the flow, its messages, feedback and upsert history. If any part fails, nothing is deleted.
-   Override configuration never takes the Agent card's knowledge lists (`agentKnowledgeDocumentStores`, `agentKnowledgeVSEmbeddings`) from a request, nor any list whose items choose an embeddings, vector store or model card. A request could otherwise add a knowledge item with no saved credential, which some providers run on a key from the server's environment.
-   Override configuration never switches the model, embeddings or vector store card a step uses (`agentModel`, `llmModel`, `conditionAgentModel`, `humanInputModel`, `embeddingModel`, `vectorStore`, and any picker that loads a card's settings). The saved credential belongs to the owner's card, and another provider could fall back to a key in the server's environment. Settings on the owner's card, such as `modelName` and `temperature` in `agentModelConfig`, still apply when allowlisted.
-   File names stored with a flow can never read outside that flow's folder (covered by tests).
-   Prediction uploads follow the flow's upload settings on the server, not only in the chat. An image, recording, document or chat file the flow does not accept is refused before anything is stored: 403 when that kind of upload is off, 400 for a file type the flow does not take. The chat, the shared chat and the embed upload as before when uploads are on.
-   A file link in an Agent's answer is signed and opens for 15 minutes without the flow's API key, for that one file in that conversation of that flow. Before, a browser user of a key-protected flow got 401 from the link. A changed or expired link is refused, and the key and session checks are unchanged.

### Good to know

Back up your data directory, including its encryption key, before any upgrade. [Upgrading Cuttlely](./docs/upgrading.md) has the steps and how to roll back.

-   **Status codes.**
    -   A prediction with `Origin: null` (sandboxed iframes, `file://` pages) or an Origin that is not a URL gets 403. Server-to-server calls without an Origin are accepted.
    -   Uploading an attachment when uploads are off for the flow returns 403. A file type the flow does not allow returns 400.
    -   A harness that cannot run returns 422 `CANNOT_RUN`. Other 4xx errors keep their status: 402 `QUOTA_EXCEEDED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 429 `RATE_LIMITED`. Anything else is 500 `INTERNAL_ERROR`.
    -   An OAuth credential refresh that the provider rejects with 401 returns 502.
-   **Streaming rule.** `/api/v1/prediction` and the canvas test chat route (`/api/v1/internal-prediction`) stream only for `streaming: true` or `streaming: "true"`. Values like `1`, `"1"` or `"TRUE"` get a JSON answer.
-   **Port overrides.** `port`, `*_port` and `*Port` settings are never taken from a request, even when allowlisted. Leave port entries out of your override configuration, and remove any that are already there. See [Override configuration](./docs/reference/override-config.md).
-   **Stream error events.** A streamed `error` event keeps the message in `data` and adds `status` and `code`.
-   **Image path.** The image's working directory is `/usr/src/cuttlely` (was `/usr/src/flowise`). Update any volume, script or shell command that used the old path. The data volume (`/var/cuttlely`) is not affected.
-   **Prediction uploads.** `POST /api/v1/prediction/:id` takes only the uploads the flow accepts. Documents sent in `files` or as uploads need file uploads on (**Configuration**, **File Upload**, **Enable Full File Upload**), images need a card with image uploads on, and audio needs Speech to Text. Others get 403 when that kind is off, or 400 for a type the flow does not take, and nothing is stored. A file for a document loader input allowed in Override Config is still taken. See [Send a file with the question](./docs/api.md#send-a-file-with-the-question).
-   **Knowledge list overrides.** `agentKnowledgeDocumentStores` and `agentKnowledgeVSEmbeddings` are never taken from a request, even when allowlisted. Remove them from your override configuration; the knowledge saved on the Agent card is used. See [Override configuration](./docs/reference/override-config.md).
-   **Card picker overrides.** `agentModel`, `llmModel`, `conditionAgentModel`, `humanInputModel`, `embeddingModel` and `vectorStore` are never taken from a request, even when allowlisted. Allowlist settings on the card instead (for example `modelName` in `agentModelConfig`). See [Override configuration](./docs/reference/override-config.md).
-   **Request variables.** Request `vars` reach `{{$vars}}` only in Multi-Agent and Sequential Agent flows. In chatflows and agentflows they reach code that reads variables, not `{{$vars}}` in a card's text. In Multi-Agent and Sequential Agent code inputs, a request value written as `{{$vars.name}}` is now inserted as escaped text: inside quotes it reads as before, outside quotes anything but a number stops that card's code with a syntax error. Read `$vars.name` in code instead. See [Request values in code inputs](./docs/reference/override-config.md#request-values-in-code-inputs).
-   **API-key chatflow list.** `GET /api/v1/chatflows/apikey/:apikey` lists only flows bound to that key, with five fields. An unknown key gets 401.
-   **OAuth refresh.** `POST /api/v1/oauth2-credential/refresh/:credentialId` needs a session or an API key with `credentials:create` or `credentials:update`. A credential in another workspace gets 404.
-   **Drafts on by default.** A canvas save starts a draft, and **Publish** makes it Live. Scripts that call `PUT /api/v1/chatflows/:id` write Live. `CUTTLELY_DRAFTS=off` makes the canvas save straight to Live.
-   **Version history on by default.** It needs `git` on `PATH`; the image includes it. `CUTTLELY_VERSIONS=off` turns it off.
-   **Model lists.** Models their providers have shut down, or shut down before November 2026, are not offered, among them `gpt-3.5-turbo`, `gpt-4`, `o1`, Claude 3 models, Gemini 1.5 and 2.0, `deepseek-chat`, `mistral-tiny` and Cohere v2 embeddings. A flow saved with one keeps that model name and still sends it, so it works for as long as the provider accepts it; pick a current model on the card to move off it.
-   **Card look.** The new card look is the default. `CANVAS_CARD_LOOK=classic` sets classic cards for everyone who has not chosen.
-   **V1 agentflows.** Existing V1 agentflows run and open from a direct link. You can't create, duplicate or save one as a template.
-   **Local account on by default.** `scripts/start-cuttlely.sh` turns the local password account on (`CUTTLELY_LOCAL_ADMIN=true`) unless you set it; a blank value counts as unset. In Docker it stays on even with WorkOS keys (Compose sets `CUTTLELY_INSTALL=docker`). From source, the start script leaves it off when `WORKOS_API_KEY` is set or `packages/server/.env` sets it. On Render it is left off. Set `CUTTLELY_LOCAL_ADMIN=false` in `.env` to keep it off.
-   **Node 24.** Running from source needs Node 24 (`.nvmrc`).
-   **Data directory.** Data lives in `~/.cuttlely`, or `/var/cuttlely/data` in Docker and on Render. Keep the encryption key with the database.
